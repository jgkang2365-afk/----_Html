# 예비조사 업무 규칙

> 현행 통합본: 2026-08-31  
> 정책 기준: 2026-08-31 사용자가 재확인·보완한 현행 업무 규칙

이 문서는 예비조사 기능의 **단일 장기 기준 문서(canonical business rule)**다. 과거 커밋, 코드 주석, 이전 작업지시서, 테스트가 이 문서와 충돌하면 현행 통합본을 우선한다. 새 업무 결정을 내리면 먼저 이 문서를 갱신하고, 이후 코드·DB·테스트를 이 기준에 맞춘다.

예비조사 추천의 날짜 기준점은 현재 날짜가 아니라 **측정예정일**이다. 정책 범위의 정상 후보를 현재보다 과거라는 이유만으로 제외하지 않는다.

## 1. 역할과 authoritative source

- 사업장 상세가 실제 업무 입력의 시작점이다. 사용자는 측정예정일, 보고서 담당자, 날짜별 측정 참여자와 다일 일정을 먼저 계획한다.
- **예비조사자**는 페이퍼상 예비조사를 수행하는 사람 또는 조합이다.
- **측정자 = 메인측정자 = 공시료 담당자**는 같은 역할이다.
- **측정 참여자**는 실제 현장 참여자다. 단일일은 `measurement_target_business.collaborators`, 다일은 해당 날짜의 `daily_staff[].collaborators`가 원천이다.
- **보고서 담당자**는 보고서 작성·관리 담당자다. 사업장 단위 기본 원천은 `measurement_target_business.measurer_id`, 다일의 날짜별 값은 해당 `daily_staff[].measurer_id`를 따른다.
- 측정 참여자의 배열 순서와 보고서 담당자 포함 여부는 측정자(공시료) 역할을 뜻하지 않는다.
- 예비조사 화면에서 측정 참여자·보고서 담당자를 임의 추론하거나 예비조사자/측정자 값에서 역산하지 않는다.
- `daily_staff.measurer_id`를 공시료 담당자로 해석하거나 `daily_staff.collaborators`의 순서로 메인 역할을 추론하지 않는다.
- 다만 **자동추천에서 예비조사자 조합을 선택할 때는 보고서 담당자와 업무상 조합 가능한 예비조사자를 우선하는 preference**를 적용한다. 이는 보고서 담당자를 측정자(공시료)로 직접 간주하는 규칙이 아니다.

## 2. 예비조사 경력 구성 — 자동추천 hard rule

경력 여부는 `users.is_preliminary_survey_experienced`만 사용하며 입사일 등으로 추론하지 않는다.

| 예비조사자 구성 | 자동추천 허용 여부 |
|---|---|
| 경력자 단독 | 허용 |
| 경력자 + 비경력자 | 허용 |
| 경력자 + 경력자 | 자동 기본조합 아님 |
| 비경력자 단독 | **금지** |

- 자동추천에는 모든 사업장 유형과 모든 방식(방문/유선)에 동일하게 적용한다.
- 자동추천 예비조사자 조합에는 **최소 1명의 경력자가 반드시 포함**되어야 한다.
- 경력자+비경력자 조합의 실제 수행 역할은 방식에 따라 구분한다. **방문은 조합 전체가 현장 예비조사 수행자**이고, **기존업체 유선은 비경력자가 유선 파악 responsible, 경력자는 결과정보를 검수하는 reviewer**다. 기존업체 유선의 reviewer를 동일일 유선 수행자로 취급하지 않는다.
- 경력자를 붙일 수 없는 날짜에 비경력자만 남는다면 `경력 검토자 미배정` 경고로 자동추천을 살려두지 않는다. **그 날짜 후보를 탈락시키고 다음 후보일을 탐색한다.**
- 경력자 2명 이상 조합은 자동추천의 기본 조합이 아니다.
- 복수 예비조사자의 **화면·목록 표시 순서는 `경력자, 비경력자` 순으로 통일**한다. 표시 순서는 실제 responsible/reviewer 역할 판정과 무관하며, 기존업체 유선에서는 표시상 경력자가 먼저 보여도 실제 전화 파악 responsible는 비경력자다.
- 경력자끼리의 표시 순서에는 별도의 업무상 우선 의미를 부여하지 않는다.
- **관리자 수정 모달의 직접 수동수정은 이 자동추천 hard rule로 저장을 차단하지 않는다.** 관리자가 자동추천 기준과 다른 조합을 저장하려는 경우 구체적인 지침 위반 경고와 확인을 표시하고, 관리자 판단으로 저장할 수 있게 한다. 데이터 형식·사용자 존재성·동시성 등 구조적 무결성 오류만 저장을 차단한다.

## 3. 업체 구분별 날짜와 방식

### 최초실시

- 방문 필수.
- 측정예정일 기준 working day `-3, -4, -5 ... -20` 순으로 탐색한다.
- `-20`을 넘는 과거일은 정상 자동추천으로 만들지 않는다.

### 타기관 신규

- **기존 확정 방식을 그대로 유지한다.**
- 방문 필수.
- primary는 working day `-20, -19 ... -3` 순으로 탐색한다.
- primary가 모두 hard constraint로 불가능할 때만 fallback `-25, -24 ... -21`을 검토한다.
- 경력 구성은 다른 사업장과 동일하게 §2의 자동추천 hard rule을 적용한다.

### 기존업체

- 유선이 기본이다.
- primary는 working day `-20, -19 ... -3`을 정책상 후보군으로 사용한다. **여러 기존업체를 배정할 때 `-20`부터 업체별로 첫 유효일을 고정해 같은 날짜에 몰아넣지 않는다.**
- primary 안에서 hard constraint를 통과한 후보일들을 대상으로 **날짜별 기존업체 유선 배정 건수를 먼저 균등화**한다. 아직 0건인 유효 후보일이 남아 있으면 이미 1건 이상 배정된 날짜에 두 번째 업체를 넣지 않는다.
- 날짜별 분산은 `0건 날짜 우선 → 모든 유효 날짜가 1건 이상이면 1건 날짜 우선 → 그 다음 2건 날짜 우선` 순으로 진행한다. 같은 날짜 건수가 같으면 기존 날짜 우선순위(`-20 → -19 → ... → -3`)를 tie-break로 사용한다.
- 날짜별 균등화는 **기존 persisted/가확정 유선 plan과 이번 추천 draft를 함께 합산**해 계산한다. 업체 배열 순서나 코드 순서 때문에 특정 날짜에 몰리지 않아야 한다.
- 위 날짜 분산 규칙은 responsible의 1일 최대 3건 capacity와 별개다. 날짜 전체에 여러 responsible가 있더라도 유효한 빈 후보일이 남아 있으면 같은 날짜 중복을 먼저 만들지 않는다.
- primary가 모두 hard constraint로 불가능할 때만 fallback `-25, -24 ... -21`을 검토하며, fallback 안에서도 같은 날짜별 균등분산 원칙을 적용한다.
- 기존업체 때문에 별도 방문일을 만들지 않는다.
- 유선 파악은 실제 측정 업무와 병행할 수 있으므로 **해당 직원에게 실제 측정 일정이 있다는 이유만으로 기존업체 유선 후보일을 제외하지 않는다.**
- 이미 같은 날 필수 신규 방문이 있고 동일주소 또는 검증된 가까운 동선이며 방문 허용량과 후발 필수방문 여유를 해치지 않을 때만 선택 방문으로 올릴 수 있다.

### 공통 날짜 규칙

- 휴일·주말은 후보에서 제외한다.
- 측정예정일에서 역산한다. KST 오늘, 실행 시각, `candidate >= today` 조건으로 과거 후보를 제거하지 않는다.
- 날짜가 정책 범위에 있다는 것만으로 정상 선택으로 보지 않는다. 더 높은 우선순위 후보가 왜 탈락했는지 설명 가능해야 한다.
- 위 날짜·방식 규칙은 **자동추천 기준**이다. 관리자 수정 모달에서 다른 날짜·방식을 직접 지정하면 저장을 막지 않고 `운영지침 위반` 경고를 표시하여 관리자가 최종 판단한다.

## 4. 자동추천 계산 순서 — hard constraint 우선

강한 제약을 먼저 해결하고 통과한 후보에 대해서만 preference를 계산한다.

1. 현재 활성 측정대상과 사업장 구분을 확정한다.
2. 사업장 유형에 따라 방식과 날짜 후보 순서를 만든다.
3. 각 후보일에서 예비조사 경력 구성 hard rule을 검사한다.
4. 방식별 실제 수행 역할에 맞춰 불가 일정을 검사한다. 방문은 현장 수행자 전원의 `user_schedule_blocks`와 실제 측정 일정 충돌을 검사한다. **기존업체 유선은 responsible의 `user_schedule_blocks`만 동일일 hard block으로 적용하며, responsible의 실제 측정 일정과 reviewer의 실제 측정 일정은 유선 후보일을 막지 않는다.**
5. 방문/유선 용량과 기존 plan·영향 범위 dependency를 검사한다. **기존업체 유선 capacity는 responsible에게만 계산하고 reviewer는 카운트하지 않는다.**
6. 기존업체 유선은 hard constraint를 통과한 후보일 전체에서 **날짜별 기존업체 유선 배정 건수를 균등화**한다. 유효한 0건 날짜가 남아 있는 동안 같은 날짜의 두 번째 배정을 만들지 않고, `0 → 1 → 2` 순환 후 동일 건수에서는 `-20 → -19 → ... → -3` 순서를 tie-break로 사용한다.
7. 방문이면 동일주소·실제 vehicle route 등 필수 동선 조건을 검사한다.
8. hard constraint를 통과한 예비조사자 조합 중 **보고서 담당자와 조합 가능한 조합을 우선한다.** 비경력 보고서 담당자는 지정 경력 reviewer와의 조합 또는 그 경력자 단독을 우선 후보로 사용한다. 경력 보고서 담당자는 해당 경력자 단독을 우선한다. 그 뒤 날짜·용량·동선·균형으로 최종 예비조사일과 예비조사자 조합을 확정한다.
9. 그 다음에 실제 측정일별 측정자(공시료)를 배정한다. **확정된 예비조사자 중 배정 가능한 사람을 우선 후보군으로 사용하고, 같은 후보군 안에서는 1인·1일·1업체·1공시료 1차 순환을 먼저 적용한다.**
10. stale/lock/찐확정/assignment 자동추천 한도를 최종 재검증한다.
11. 임시 draft를 사용자에게 보여주고 확인 후 적용한다.

- 공시료 정합성이나 코드 순서 때문에 경력·일정·용량 hard rule을 깨지 않는다.
- 추천 생성은 임시 draft만 만들고 DB를 변경하지 않는다.
- 저장 직전 원천값, baseline, hard constraint가 달라지면 다른 안을 자동 저장하지 않고 재검토를 요구한다.

## 5. 조사량·용량·직원 불가 일정

### 방문

- 하루 1건이 원칙이다.
- 동선이 명확히 적합할 때 최대 2건까지 자동추천할 수 있다.
- 같은 직원의 기존 manual/가확정 방문, 영향 범위 밖 유지 방문, 새 추천 방문을 모두 합산한다.
- 실제 vehicle route 30분 이하는 same-route를 적극 우선한다.
- 31~60분은 더 적합한 단독 날짜가 없을 때의 fallback 검토 범위로 둔다.
- 60분 초과는 같은 날 묶지 않는다.
- route evidence가 없으면 동일주소 외 자동 근거리 판정을 확정 근거로 사용하지 않는다.

### 유선

- 기존업체 유선의 **실제 수행자는 responsible 1명**이다.
- 경력자 단독이면 해당 경력자가 responsible로 유선 파악을 수행한다.
- 경력자+비경력자 조합이면 **비경력자가 responsible로 전화·유선 파악을 수행하고, 경력자는 예비조사 결과정보를 검수하는 reviewer 역할만 수행한다.**
- 기존업체 유선에서 비경력 responsible별 **우선 경력 reviewer 조합**은 다음과 같다.

| 비경력 responsible | 우선 경력 reviewer | 화면 표시 |
|---|---|---|
| 강종구 | 이태환 | 이태환, 강종구 |
| 고유빈 | 이주형 | 이주형, 고유빈 |
| 김민영 | 한기문 | 한기문, 김민영 |

- 위 조합은 기존업체 유선의 **우선 적용 조합**이다. 경력 구성 hard rule을 충족하는 범위에서 해당 조합을 먼저 사용한다.
- **보고서 담당자 조합 preference:** 보고서 담당자가 강종구이면 `이태환, 강종구` 조합 또는 `이태환` 단독, 고유빈이면 `이주형, 고유빈` 조합 또는 `이주형` 단독, 김민영이면 `한기문, 김민영` 조합 또는 `한기문` 단독을 다른 무관한 조합보다 우선한다. 보고서 담당자가 이태환·이주형·한기문 같은 경력자이면 해당 경력자 단독을 우선한다. hard constraint로 불가능할 때만 다른 정상 조합으로 fallback한다.
- 다일에서 날짜별 보고서 담당자가 서로 다르면 해당 사업장의 실제 측정일별 보고서 담당자 원천을 모두 고려해 조합 가능한 후보를 만들고, 한 날짜의 보고서 담당자를 다른 날짜 원천으로 덮어쓰지 않는다.
- 동일 예비조사일·동일 responsible 기준 자동추천은 1인당 최대 3개다.
- 날짜 선택 자체도 균등분산한다. **유효한 다른 후보일에 기존업체 유선 배정이 0건이면 이미 사용한 날짜에 두 번째 업체를 배정하지 않는다.** 모든 유효 날짜가 한 번씩 사용된 뒤에만 두 번째 순환을 허용하고, 이후에도 같은 방식으로 세 번째 순환을 적용한다.
- reviewer는 동일일 유선 수행자가 아니므로 **유선 3건 capacity, 방문 수행량, responsible 균등배정, 날짜별 유선 배정 건수에 카운트하지 않는다.**
- 기존업체 유선은 실제 측정 업무와 병행 가능하므로 **responsible 또는 reviewer에게 실제 측정 일정이 있다는 사실 자체를 유선 후보일 hard block으로 사용하지 않는다.**
- 정상 운영 데이터에서는 primary와 fallback 후보를 통틀어 responsible의 1일 3건 capacity로 날짜를 분산하므로 **기존업체 유선 추천일이 `null`인 상태를 정상 PASS로 인정하지 않는다.** `null`이 발생하면 먼저 실제 측정 일정이나 reviewer capacity를 잘못 hard block했는지 구현 오류로 판정한다. 모든 후보일이 responsible의 명시적 `user_schedule_blocks` 또는 이미 찬 유선 3건 capacity로 막힌 사실이 입증된 경우에만 사용자 판단 대상으로 남긴다.

### 직원 불가 일정

- `user_schedule_blocks`는 실제 수행자의 명시적 불가 일정 원천이다.
- 방문 예비조사는 현장 수행자 전원에게 적용한다.
- 기존업체 유선은 **실제 전화 파악 responsible에게만 동일일 hard block으로 적용한다.** reviewer는 동일일 수행량을 소비하지 않는 검수 역할이므로 예비조사일 선정의 hard block 대상으로 사용하지 않는다.
- 측정자(공시료), 측정 참여자, 보고서 담당자 등 각 실제 업무 역할의 **자동 신규 배정**에는 기존 불가 일정 정책을 유지한다.
- 불가 일정은 자동추천의 공시료 균등배정, 동일주소, 동선, 관리자 3건 예외보다 우선하는 hard constraint다.
- 계획 생성 후 불가 일정이 추가되면 가확정은 `재검토 필요`로 표시한다. 찐확정은 자동 변경하지 않는다.
- 관리자가 수정 모달에서 불가 일정 직원 등을 직접 선택하는 경우에도 **경고는 표시하지만 관리자의 수동 저장을 업무지침만으로 차단하지 않는다.**

## 6. 측정자(공시료)와 코드

고정 base code:

| 측정자 | base code |
|---|---|
| 이태환 | A |
| 한기문 | B |
| 강종구 | C |
| 이주형 | D |
| 고유빈 | F |
| 김민영 | G |

동일 측정일·동일 측정자의 배정 수에 따라 base를 반복한다.

- 1건: `C`
- 2건: `C`, `CC`
- 3건: `C`, `CC`, `CCC`
- 관리자 수동수정으로 4건 이상을 명시적으로 선택한 경우에도 같은 원리로 `CCCC`처럼 base code를 배정 수만큼 반복하여 날짜 그룹 전체를 정규화한다. 이 경우 운영지침 초과 경고와 audit을 남긴다.

A/B/D/F/G도 동일한 방식으로 적용한다.

- 코드는 **해당 실제 측정일의 동일 담당자 assignment 그룹 안에서 정규화되는 값**이다. 특정 사업장에 base code를 영구 고정하지 않는다.
- 예를 들어 같은 날 강종구가 2개 사업장을 맡으면 두 사업장 중 하나는 `C`, 다른 하나는 `CC`다. 어느 사업장이 `C` 또는 `CC`가 되는지는 그 날짜 그룹의 안정적인 정규화 순서로 결정하며, 두 사업장이 모두 `C`가 되어서는 안 된다.

### 사업장별·측정일별 공시료 assignment

- **공시료 배정 단위는 `실제 측정일 × 사업장` 1건**이다. 같은 사업장이라도 실제 측정일이 여러 날이면 각 측정일마다 공시료 assignment를 1건씩 가진다.
- 따라서 **1개 사업장에는 각 실제 측정일마다 공시료 1개**가 대응한다. 한 공시료 assignment를 여러 사업장에 공동으로 쓰거나, 한 사업장의 이전 측정일 assignment를 다음 측정일에 그대로 복사하지 않는다.
- 다일 사업장의 예비조사일·예비조사자 plan은 공유하지만, 측정자(공시료)는 **각 실제 측정일의 전체 사업장 배정 상황을 기준으로 그 날짜마다 다시 계산**한다.
- 같은 실제 측정일에 동일 측정자에게 2개 사업장이 배정되면 해당 두 사업장의 코드는 base와 2회 반복 코드로 정규화한다. 예: 강종구가 같은 날 2개 사업장의 측정자(공시료)라면 `C`, `CC`를 각각 1개 사업장에 부여한다.
- 같은 날짜의 담당자 또는 사업장 집합이 바뀌면 영향을 받는 해당 날짜 assignment 그룹 전체를 다시 정규화한다. 앞선 날짜의 `C`, `CC` 등 코드 순서를 다음 측정일에 carry-forward하지 않는다.

### 자동추천 한도와 관리자 직접수정

- **자동추천 기본은 1인·1일·1업체·1공시료다.** 동일 우선 후보군에서 아직 당일 배정이 0건인 배정 가능자가 남아 있으면 이미 1건을 받은 사람에게 두 번째 업체를 배정하지 않는다.
- 자동추천에서 예비조사자 중 배정 가능한 사람이 있으면 그들을 1차 후보군으로 사용한다. 여러 명이면 그 후보군 안에서 당일 0건인 사람을 먼저 사용하고, 그 다음 현재 배정수가 적은 사람을 우선한다.
- 예비조사자 중 당일 배정 가능한 사람이 한 명도 없을 때만 다른 측정자를 fallback 후보군으로 검토한다. 이 경우 예비조사자↔측정자 불일치 사유를 명시한다.
- 동일 우선 후보군의 배정 가능한 사람이 모두 1건씩 받은 뒤에도 추가 사업장이 남는 경우에만 동일인 두 번째 업체를 자동 검토한다. 두 번째 업체까지는 해당일 그룹 코드 정규화로 `C/CC`, `A/AA` 등 서로 다른 코드를 부여한다.
- 자동추천의 정확히 3건은 동일주소·가까운 동선 등 실제 수행 가능성을 **관리자가 직접 검토한 명시 예외**에서만 허용한다.
- 자동추천 4건 이상은 hard block한다.
- 위 자동추천 한도는 **관리자 수정 모달의 직접 수동지정 한도가 아니다.** 관리자가 3건·4건 이상을 직접 지정하면 지침 초과 경고와 확인을 표시하고 저장할 수 있으며, 동일일 영향 그룹 코드를 전체 재정규화하고 audit을 남긴다.

## 7. 예비조사자 ↔ 측정자(공시료) 서류 정합성

예비조사의 핵심 서류 정합성은 **예비조사자와 측정자(공시료)의 관계**로 평가한다.

- 단일일 측정은 예비조사자 중 **한 명이라도** 측정자(공시료)와 일치하면 match다.
- 다일 측정은 각 실제 측정일별로 예비조사자 중 배정 가능한 사람을 우선한다. 전체 측정기간 중 최소 하루라도 match이면 기간 단위 정합성 match로 볼 수 있지만, 개별 날짜에서 예비조사자가 배정 가능한데도 임의의 외부 측정자를 먼저 선택하지 않는다.
- 예비조사자 중 당일 배정 가능한 사람이 없어서 다른 측정자를 써야 하는 불일치는 실무상 가능하므로 자동추천 hard fail하지 않지만, fallback 사유를 반드시 남긴다.
- **보고서 담당자는 공시료 담당자로 직접 변환하지 않는다.** 보고서 담당자는 §4·§5에 따라 예비조사자 조합 preference를 만드는 데 사용하고, 공시료는 그 결과 확정된 예비조사자 후보군에서 배정한다.
- 측정 참여자는 공시료 match 점수에 직접 사용하지 않는다.

측정자(공시료) 자동 배정 우선순위는 다음과 같다.

1. 해당 사업장의 확정 예비조사자 중 당일 배정 가능한 사람을 우선 후보군으로 확정
2. 같은 후보군에서 `0건 → 1건` 순으로 1인·1일·1업체·1공시료 1차 순환
3. 같은 배정 회차에서 현재 배정수가 적은 사람 우선
4. 동일주소
5. 실제 차량 동선
6. 안정적인 ID
7. 예비조사자 후보군이 모두 불가능할 때만 다른 측정자 fallback

한 사람이 두 번째 업체를 받기 전에 **같은 우선 후보군**에 아직 0건인 배정 가능자가 있으면 그 사람을 먼저 사용한다. 6명에게 6개 업체를 각각 match 상태로 배정할 수 있으면 기본 목표는 `1/1/1/1/1/1`이다.

## 8. 다일 측정

- `daily_staff`에 명시된 모든 실제 측정일을 사용한다. 시작일~종료일 사이 날짜를 임의 생성하지 않는다.
- 예비조사 plan은 사업장당 하나만 유지한다.
- 같은 사업장의 모든 실제 측정일은 동일한 예비조사일·방식·예비조사자·상태·확정정보를 공유한다.
- 날짜별 새 예비조사 plan을 중복 생성하지 않는다.
- 측정자(공시료) assignment는 **실제 측정일별·사업장별로 독립 관리**한다. 예비조사 plan에서 앞선 측정일의 측정자(공시료)와 코드를 가져와 다음 날짜에 그대로 사용하지 않는다.
- 각 실제 측정일마다 그 날짜에 측정하는 모든 사업장의 공시료 배정 현황을 다시 계산하고, 동일 담당자의 당일 사업장 수에 따라 `C/CC/CCC/...` 등 코드를 그 날짜 기준으로 정규화한다.
- 예: H0508처럼 2일 이상 측정하는 사업장은 예비조사일·예비조사자는 동일 plan에서 가져온다. 그러나 두 번째 측정일의 측정자(공시료)는 그날의 전체 배정 상황을 기준으로 다시 정한다. 강종구가 그날 H0508을 포함해 2개 사업장의 측정자라면 두 사업장은 각각 `C`, `CC`를 가져야 한다.
- 예: 한 사업장이 8/03과 8/25에 측정하면 두 날짜 검색에서 모두 노출되지만 예비조사 plan은 하나다. 8/03 기준으로 이미 유효한 예비조사가 있으면 8/25 때문에 새 plan을 만들지 않지만, 8/25의 공시료 assignment는 8/25 당일 기준으로 별도 계산한다.

## 9. 기준 데이터 흐름과 표시

기준 흐름은 다음과 같다.

`measurement_target_business → 예비조사 plan/assignment → measurement_journal`

- 현재 target이 존재하면 측정일지 검색도 target의 유효 측정일과 lifecycle(`실시`)을 따른다.
- `미실시`·`거래종료` target에 연결된 과거 journal row는 삭제하지 않지만 현재 검색·표시에서는 제외한다.
- target 자체가 없는 순수 과거 이력은 이 기준으로 삭제하거나 수정하지 않는다.
- 측정 참여자와 보고서 담당자의 불일치는 별도 경고 대상이 될 수 있으나 예비조사자↔공시료 정합성 hard validation이 아니다.
- 예비조사 계획과 목록의 기본 표시 순서는 측정대상 사업장 관리의 canonical 기본 조회순서(상태 → 예정월 → 코드)를 공유한다.
- 예비조사자 복수 표시에서는 **항상 경력자를 먼저, 비경력자를 뒤에 표시**한다. 이 표시는 보기 순서일 뿐 실제 업무 역할을 뒤집지 않는다.
- 날짜별 목록의 `측정자(공시료)` 칸은 **해당 조회일의 실제 assignment를 `이름(코드)`로만 표시**한다. 목록 셀 안에 측정일 문자열을 다시 붙이지 않는다.
- 동일 측정일에 같은 담당자가 여러 사업장을 맡으면 각 행은 해당 날짜 그룹의 정규화 결과를 그대로 표시한다. 따라서 강종구가 같은 날 2개 사업장을 맡은 경우 한 행은 `강종구(C)`, 다른 행은 `강종구(CC)`가 될 수 있으며 특정 사업장에 `C`를 고정하지 않는다.
- 다일 전체 날짜별 공시료 내역이 필요한 경우 상세 화면에서 날짜별 assignment를 확인하고, 날짜별 목록 요약 칸에는 다른 날짜의 assignment를 병합 표시하지 않는다.
- 예비조사 수정 모달의 헤더는 **`예비조사 상세`**로 짧게 고정하고, 업체명은 본문 상단에 **`업체명 : {사업장명}`** 형식으로 별도 표시한다. 긴 업체명은 줄바꿈되어 모달 폭을 넘지 않아야 한다.
- 수정 모달에는 헤더의 닫기 아이콘과 별개로 사용자가 명확히 확인할 수 있는 **`닫기` 버튼**을 제공한다.

## 10. 찐확정과 repair

- `measurement_journal` row가 존재하면 찐확정이다.
- `sequence_number`는 찐확정 판정 기준으로 사용하지 않는다.
- 찐확정은 **자동추천·자동재추천·자동삭제**의 변경 대상에서 제외한다.
- 찐확정도 현행 날짜 정책과 비교하여 정책 불일치 또는 mapping 오류를 검출한다.
- 관리자 또는 예비조사 담당자의 기존 repair 경로는 계속 사용할 수 있다.
- **관리자는 수정 모달에서 찐확정 여부와 관계없이 예비조사일·방식·예비조사자·날짜별 측정자(공시료)를 직접 수정할 수 있다.** 이 관리자 직접수정은 `measurement_journal`을 삭제·재생성하거나 측정예정일·측정 참여자·보고서 담당자 원천을 자동 변경하지 않는다.
- 관리자 직접수정이 현행 운영지침을 벗어나면 저장 차단 대신 구체적인 경고와 확인을 제공하고, 저장 시 before/after·경고 내용·수정자·시각을 audit에 남긴다.
- 예비조사 담당자 권한만 있는 사용자는 찐확정에 대해 기존 repair 경로와 보호 규칙을 따른다.
- 과거 당시의 불가 일정·용량을 재현할 수 없는 fallback 날짜는 자동 위반으로 단정하지 않고 수동 검토 대상으로 처리한다.

### 측정 참여자·보고서 담당자 source repair

- 측정 참여자와 보고서 담당자는 서로 독립적으로 보정한다.
- 관리자 예비조사 수정 모달의 일반 수동수정도 **코드, 사업장명, 구분, 측정예정일/다일 실제 측정일, 측정 참여자, 보고서 담당자**를 연쇄 변경하지 않는다. 이 원천들은 별도 원천 repair 기능에서만 명시적으로 수정한다.
- 선택하지 않은 역할, 측정일지와 과거 row를 자동 변경하지 않는다.
- before/after·사유·수정자를 audit에 남긴다.

## 11. 수동 수정·재추천·삭제

### 자동추천·일반 권한 경로

- 관리자 또는 `users.is_preliminary_survey_manager = true`가 추천·재추천·적용·일반 repair를 수행한다.
- 자동추천의 1인 3건 공시료 예외는 관리자만 승인한다.
- 비찐확정 plan의 날짜별 공시료 수동수정은 기존 권한자가 수행할 수 있으며 일반 권한 경로에서는 자동추천 한도와 안전 규칙을 따른다.
- 예비조사 담당자만으로 찐확정 보호를 우회하거나 자동추천 4건 이상을 승인할 수 없다.
- 일반 사용자는 조회 중심이다.

### 관리자 수정 모달 — 직접 수동수정 우선 원칙

- **관리자(`role = 관리자`) 수정 모달은 업무 판단을 반영하는 최종 수동수정 화면이다.** 관리자에게 자동추천 결과를 강제로 유지시키지 않는다.
- 관리자는 찐확정 여부와 관계없이 다음 항목을 직접 수정할 수 있다.
  - 예비조사일
  - 방문/유선 방식
  - 예비조사자
  - 기존업체 유선 responsible/reviewer 결과
  - 실제 측정일별 측정자(공시료)
- 다일 사업장은 실제 측정일별 공시료를 각각 독립 선택할 수 있어야 한다.
- 관리자 입력이 날짜범위, 방식, 경력조합, 불가일정, 자동추천 용량, 예비조사자↔공시료 정합성, 1일 권장 건수 등 운영지침과 다르면 **구체적인 경고 목록을 표시한다. 지침 위반만으로 저장 버튼을 비활성화하거나 서버가 저장을 거부하지 않는다.**
- 경고가 있으면 저장 전에 `운영지침 위반 사항`을 보여주고 관리자 확인 후 저장한다.
- 관리자 공시료 직접수정 후에는 같은 실제 측정일의 이전 담당자 그룹과 신규 담당자 그룹 전체를 원자적으로 재정규화한다. `C/CC/CCC/CCCC...`처럼 동일일 배정 순서에 맞게 반복코드를 만든다.
- 관리자 직접수정은 찐확정 trigger를 일반적으로 해제하는 것이 아니라 **관리자 전용 서버 RPC/transaction 안에서만 제한적으로 bypass**한다.
- 구조적 무결성·보안 오류는 여전히 저장을 차단한다. 예: 존재하지 않는 target/사용자, 비활성·비측정 직무 사용자를 식별할 수 없음, 날짜 형식 오류, stale source/동시성 충돌, transaction 실패, 권한 위조.
- 관리자 직접수정 후 clean-room draft나 과거 draft가 화면에 남아 새 저장값을 덮어 보여서는 안 된다. 저장 성공 시 관련 draft를 폐기하고 DB를 재조회한다.
- 관리자 수정 전후 plan/assignment, 지침 경고, 수정자, 수정시각을 audit에 남긴다.

### 공통

- 기존 V2 자동추천은 OFF 상태를 유지한다. 사업장 상세 저장만으로 V2 plan을 자동 생성·확정하지 않는다.
- 기존 manual plan도 자동추천에서 minimum-change 대상으로 사용할 때는 현행 hard constraint를 다시 통과해야 한다.
- 업체별 재추천은 같은 예비조사일의 조사자/조합, 방문·유선 용량, 동일주소·방문 묶음, 다일을 포함한 같은 실제 측정일의 공시료 균형 관계를 dependency closure로 확장한다.
- 찐확정은 자동추천 dependency 계산에는 포함하되 자동 변경 대상에서는 제외한다.

### V2 plan 안전 삭제

- 찐확정되지 않은 persisted V2 plan은 예비조사 담당자 또는 관리자가 삭제할 수 있다.
- 삭제 대상은 `preliminary_survey_v2_plans`와 해당 plan에 귀속된 `preliminary_survey_v2_measurement_assignments`다.
- `measurement_target_business`, 측정예정일, `measurement_journal`, legacy 원천은 삭제하지 않는다.
- true-confirmed plan과 legacy reconciliation 또는 historical recovery 추적에 사용된 plan은 일반 삭제할 수 없다.
- 삭제 후 영향을 받는 공시료 assignment 그룹은 **자동추천 규칙의 1차 1건 우선 → 필요 시 2차 최대 2건 자동 → 관리자 3건 예외 → 4건 hard max** 원칙에 맞게 같은 transaction에서 재정규화한다.

## 12. 저장·동시성·보안 불변식

- 측정자(공시료)의 authoritative source는 `preliminary_survey_v2_measurement_assignments`다.
- 과거 `recommendation_reason.measurementAssignee`는 read-only 표시 fallback일 뿐 새 write나 자동 backfill 근거로 사용하지 않는다.
- plan과 날짜별 assignment는 최종 wrapper RPC 한 transaction에서 저장한다.
- apply 서버는 현재 원천으로 예비조사와 공시료를 다시 계산하고 canonical draft, source fingerprint, 기존 assignment baseline을 비교한다.
- 클라이언트가 보낸 사용자 ID·이름·공시료 코드·승인 필요 boolean을 authoritative 판단 근거로 신뢰하지 않는다.
- 같은 측정일의 영향 assignment 그룹은 transaction advisory lock 등으로 직렬화한다.
- source/baseline이 달라지면 stale로 판단하고 0건 저장 후 재검토를 요구한다.
- 찐확정 guard는 plan/assignment의 INSERT·UPDATE·DELETE에서 OLD와 NEW target을 모두 검사한다.
- **관리자 수정 모달의 직접수정만 관리자 전용 서버 RPC 안에서 guard를 제한적으로 우회**하며, 일반 경로·클라이언트 직접 호출에서 guard를 우회하지 않는다.
- 관리자 전용 직접수정 RPC도 역할을 서버에서 재확인하고 append-only audit, advisory lock/row lock, stale 검사를 수행한다.
- 이미 적용된 migration을 고쳐 쓰지 않고 forward-only migration으로 수정한다.
- 운영 적용 전 비운영 DB에서 migration/RPC, rollback, 권한, 동시성을 검증한다.

## 14. 회귀 검증 사례

아래 사례는 정책을 구현·검증할 때 사용하는 **회귀 fixture**다. 실제 운영일정이 변하면 날짜는 다시 계산할 수 있으나, 이 사례가 검증하려는 역할 규칙을 임의로 바꾸지 않는다.

### 2026-08-31 측정예정 6개 사업장 역할 정합성 사례

| 코드 | 예비조사자 | 유선 responsible | 경력 reviewer | 측정자(공시료) | 경력 구성 | 정합성 |
|---|---|---|---|---|---|---|
| H0028 | 이태환 | 이태환 | - | 이태환(A) | 경력자 단독 | match |
| H0033 | 이태환, 강종구 | **강종구** | 이태환 | 강종구(C) | 경력자+비경력자 | match |
| H0195 | 이주형, 고유빈 | **고유빈** | 이주형 | 고유빈(F) | 경력자+비경력자 | match |
| H0049 | 한기문 | 한기문 | - | 한기문(B) | 경력자 단독 | match |
| H0361 | 이주형 | 이주형 | - | 이주형(D) | 경력자 단독 | match |
| H0130 | 한기문, 김민영 | **김민영** | 한기문 | 김민영(G) | 경력자+비경력자 | match |

표의 공시료 코드는 해당 측정일에 각 담당자가 이 사업장 1건만 맡는 조건의 base 결과다. 같은 실제 측정일에 동일 담당자의 다른 사업장이 함께 배정되면 해당 날짜 그룹 전체를 다시 정규화하므로 특정 사업장의 코드는 `C` 대신 `CC`, `A` 대신 `AA` 등이 될 수 있다. **한 사업장에 base code를 영구 고정하는 fixture로 해석하지 않는다.**

이 사례에서 검증할 사항:

- 자동추천에 비경력자 단독 추천이 없어야 한다.
- 기존업체 유선의 경력자+비경력자 조합은 **비경력자 responsible + 경력 reviewer**로 해석하며, reviewer는 유선 capacity나 동일일 실제 측정 충돌에 카운트하지 않는다.
- 기존업체 유선의 비경력 responsible 우선 조합은 **강종구→이태환, 고유빈→이주형, 김민영→한기문**이다.
- 복수 예비조사자의 표시 순서는 **경력자, 비경력자**로 고정하며 표시 순서 자체는 responsible 판정 근거가 아니다.
- 복수 예비조사자는 구성원 중 당일 배정 가능한 사람이 있으면 그 사람을 공시료 후보군으로 먼저 사용한다.
- 공시료 6명이 각각 해당 사업장의 예비조사자 후보군으로 배정 가능하면 6개 사업장은 `1/1/1/1/1/1` 균등배정을 우선한다.
- 예비조사일은 위 역할 조합을 임의 변경하지 않고 측정예정일에서 현행 날짜·hard constraint 규칙으로 역산한다.
- **보고서 담당자 조합 회귀:** 보고서 담당자가 고유빈인 기존업체라면 hard constraint가 허용하는 범위에서 `이주형, 고유빈` 또는 `이주형`이 다른 무관한 예비조사자 조합보다 우선되어야 한다. 강종구·김민영도 각각 `이태환`·`한기문` 조합 원칙을 동일하게 적용한다.
- **기존업체 유선인 6건 모두 정상 운영 데이터에서 예비조사일이 산출되어야 하며, 특히 H0049를 `null`/미배정으로 두고 PASS 처리하면 안 된다.** `null`이 나오면 실제 측정 일정 또는 reviewer를 잘못 hard block하거나 capacity를 중복 계산한 구현 오류를 우선 의심한다.
- 동일 측정예정일의 기존업체 유선 6건에 서로 다른 유효 primary 후보일이 6일 이상 있으면 **6건을 서로 다른 예비조사일에 먼저 분산**한다. 첫 업체가 `-20`을 사용했다는 이유로 나머지 업체를 같은 `-20` 날짜에 몰아넣지 않는다. 모든 유효 후보일을 한 번씩 사용하기 전에는 같은 날짜의 두 번째 배정을 허용하지 않는다.
- **다일 공시료 회귀:** H0508처럼 2일 이상 측정하는 사업장은 예비조사일·예비조사자를 공유하되, 각 실제 측정일의 공시료는 당일 전체 사업장 배정을 기준으로 독립 계산한다. 같은 날 강종구가 2개 사업장을 맡으면 두 사업장에 `C`, `CC`가 각각 하나씩 배정되어야 하며 앞선 측정일 코드를 그대로 복사하면 FAIL이다.
- 관리자 수정 모달에서 찐확정 H0508 같은 사업장의 날짜별 공시료를 직접 바꿀 수 있어야 하며, 같은 측정일 영향 그룹 코드가 즉시 재정규화되어야 한다.
- 관리자 수정 모달에서 최초실시를 유선으로 지정하거나 날짜범위를 벗어나게 지정하는 등 운영지침 위반 입력을 해도 저장 자체는 가능해야 하며, 저장 전 구체적인 경고와 관리자 확인이 있어야 한다.
- 관리자 수동 저장 후 이전 clean-room draft가 새 DB 값을 덮어 표시하면 FAIL이다.
- 수정 모달 헤더의 긴 업체명이 닫기 버튼을 밀어내면 FAIL이다. 헤더는 `예비조사 상세`, 업체명은 본문 `업체명 : ...`, 하단 `닫기` 버튼을 확인한다.

## 15. 운영지침 변경 절차

업무 규칙 변경 시 다음 순서를 지킨다.

1. 사용자가 최종 결정한 내용을 이 문서에 먼저 반영한다.
2. 문서 전체에서 새 결정과 충돌하는 과거 문구를 전수 검색해 **삭제한다.** 과거 규칙의 이력은 Git 커밋으로 추적한다.
3. 실제 사용자 예시가 있다면 회귀 fixture로 고정할지 검토한다.
4. `BUSINESS_LOGIC.md`, `project_rules.md`, `AGENTS.md` 등 상위 안내 문서에 중복·충돌하는 예비조사 규칙이 없는지 확인한다.
5. 그 다음 코드·DB·테스트를 이 문서에 맞춘다.
6. Fresh verifier는 코드가 현재 문서를 구현했는지 독립 검증한다.

문서와 코드가 충돌하면 구현을 임의로 정답으로 간주하지 않는다.
