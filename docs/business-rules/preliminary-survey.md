# 예비조사 업무 규칙

> 현행 통합본: 2026-09-01  
> 정책 기준: 2026-09-01 사용자가 승인한 실제 측정팀 정합성 및 측정자 고정형 역산 플래너 운영 규칙

이 문서는 예비조사 기능의 **단일 장기 기준 문서(canonical business rule)**다. 과거 커밋, 코드 주석, 이전 작업지시서, 테스트가 이 문서와 충돌하면 현행 통합본을 우선한다. 새 업무 결정을 내리면 먼저 이 문서를 갱신하고, 이후 코드·DB·테스트를 이 기준에 맞춘다.

예비조사 날짜의 기준점은 현재 날짜가 아니라 **측정예정일**이다. 정책 범위의 정상 후보를 현재보다 과거라는 이유만으로 제외하지 않는다.

2026년 9월 1일부터의 실운영 우선 경로는 사용자가 실제 측정일별 측정자(공시료 담당자)를 명시적으로 확정한 뒤, 그 확정값을 바꾸지 않고 예비조사일·방식·예비조사자를 역산하는 **측정자 고정형 역산 플래너**다. 이 플래너는 임시 보정 코드가 아니라 향후 전체 결정론적 배정 엔진에서도 재사용하는 공통 도메인 계산기로 유지한다.

## 1. 역할과 authoritative source

- 사업장 상세가 실제 업무 입력의 시작점이다. 사용자는 측정예정일, 보고서 담당자, 날짜별 측정 참여자와 다일 일정을 먼저 계획한다.
- **예비조사자**는 페이퍼상 예비조사를 수행하는 사람 또는 조합이다.
- **측정자 = 메인측정자 = 공시료 담당자**는 같은 역할이다.
- **고정 측정자**는 사용자가 특정 실제 측정일에 대해 명시적으로 확정한 측정자(공시료 담당자)다. 기존 assignment row가 존재한다는 사실만으로 사용자 확정값으로 간주하지 않는다.
- **측정 참여자**는 업무량 등의 이유로 측정자와 같은 실제 측정일에 함께 현장으로 이동하는 직원이다. 단일일은 `measurement_target_business.collaborators`, 다일은 해당 날짜의 `daily_staff[].collaborators`가 원천이다.
- **실제 측정팀**은 해당 실제 측정일의 `고정 측정자 + 측정 참여자` 합집합이다. 같은 사람이 양쪽에 중복되면 한 명으로 정규화한다.
- **보고서 담당자**는 보고서 작성·관리 담당자다. 사업장 단위 기본 원천은 `measurement_target_business.measurer_id`, 다일의 날짜별 값은 해당 `daily_staff[].measurer_id`를 따른다.
- **예비조사표 작성자**는 예비조사 결과를 실제 표로 작성하는 사람이다. 경력자 단독이면 해당 경력자, 경력자+비경력자 조합이면 비경력자가 작성자다.
- 측정 참여자의 배열 순서와 보고서 담당자 포함 여부는 측정자(공시료) 역할을 뜻하지 않는다.
- 측정 참여자와 보고서 담당자의 원천값을 예비조사자·고정 측정자에서 역산해 생성하거나 변경하지 않는다.
- `daily_staff.measurer_id`를 공시료 담당자로 해석하거나 `daily_staff.collaborators`의 순서로 메인 역할을 추론하지 않는다.
- 보고서 담당자는 역산 플래너가 변경하지 않는다. hard constraint를 통과한 후보끼리 비교할 때 업무상 가능한 예비조사자 조합의 preference로만 사용한다.
- 보고서 담당자는 고정 측정자 또는 측정 참여자로 명시되어 있지 않은 한 실제 측정팀에 자동 포함하지 않는다.

### 고정 측정자 확인

- 고정 측정자는 실제 측정일별로 별도 선택·확정한다. 다일 사업장의 한 날짜 값을 다른 날짜에 자동 복사하지 않는다.
- 측정자 선택 UI에서는 해당 실제 측정일의 측정 참여자를 우선 표시하고, 그 밖의 활성 측정 직원을 후순위로 표시한다.
- 측정 참여자에 없는 직원을 측정자로 선택하는 것은 가능하다. 다만 `측정 참여자에 포함되지 않은 측정자` 경고를 표시하고 사용자의 명시적 확인을 받아야 하며, 측정 참여자 원천을 자동 변경하지 않는다.
- 고정 측정자 확정에는 최소한 확정자, 확정시각, 확정 경로와 원천 snapshot을 식별할 수 있는 기록을 남긴다.
- 고정 측정자가 바뀌면 그 값을 전제로 만든 미적용 역산 draft는 즉시 무효화하고 다시 계산한다.

## 2. 예비조사 경력 구성과 예비조사표 작성자 — 자동결정 hard rule

경력 여부는 `users.is_preliminary_survey_experienced`만 사용하며 입사일 등으로 추론하지 않는다.

| 예비조사자 구성 | 자동결정 허용 여부 | 예비조사표 작성자 |
|---|---|---|
| 경력자 단독 | 허용 | 해당 경력자 |
| 경력자 + 비경력자 | 허용 | 비경력자 |
| 경력자 + 경력자 | 자동 기본조합 아님 | 관리자 수동결정 시 명시 |
| 비경력자 단독 | **금지** | 해당 없음 |

- 자동결정에는 모든 사업장 유형과 모든 방식(방문/유선)에 동일하게 적용한다.
- 자동결정 예비조사자 조합에는 **최소 1명의 경력자가 반드시 포함**되어야 한다.
- 경력자+비경력자 조합의 실제 역할은 방식에 따라 구분한다.
  - 방문: 조합 전체가 현장 예비조사 수행자이며, 비경력자가 예비조사표를 작성한다.
  - 기존업체 유선: 비경력자가 유선 파악 responsible이자 예비조사표 작성자이고, 경력자는 결과정보 reviewer다.
- 경력자를 붙일 수 없는 날짜에 비경력자만 남으면 경고로 후보를 살려두지 않는다. 해당 후보를 탈락시키고 다음 날짜·다른 경력 파트너를 탐색한다.
- 경력자 2명 이상 조합은 자동결정의 기본 조합이 아니다.
- 복수 예비조사자의 화면·목록 표시 순서는 `경력자, 비경력자`로 통일한다. 표시 순서는 responsible·reviewer·작성자 역할 판정 근거가 아니다.
- 경력자끼리의 표시 순서에는 별도의 업무상 우선 의미를 부여하지 않는다.

### 예비조사표 작성 업무 균등배분

- 균등배분 카운터는 일반적인 현장 방문 횟수가 아니라 **예비조사표 작성 업무량**을 분산하기 위한 preference다.
- 경력자 단독이면 해당 경력자의 작성 카운터를 1 증가시킨다.
- 경력자+비경력자이면 비경력자의 작성 카운터만 1 증가시키고 경력 파트너는 작성 카운터에서 제외한다.
- 다일 사업장도 예비조사 plan과 표가 사업장당 하나이면 작성 카운터는 1건으로 계산한다.
- 작성 카운터에서 제외된 경력자라도 방문 조합의 실제 수행자이면 직원 불가 일정·실제 측정 일정 충돌·방문 capacity에는 포함한다.
- 작성 업무 균등은 hard constraint가 아니다. 날짜·경력·일정·용량·실제 측정팀 정합성·동선을 모두 통과한 후보끼리 비교할 때만 사용한다.

### 관리자 직접수정

- 관리자 수정 모달의 직접 수동수정은 자동결정 hard rule과 별도 경로다.
- 관리자가 자동 기준과 다른 조합을 저장하려는 경우 구체적인 지침 위반 경고, 예외 사유, 명시 확인과 audit을 남기고 관리자 판단으로 저장할 수 있다.
- 데이터 형식, 사용자 존재성, 권한, 동시성, transaction 등 구조적 무결성 오류는 관리자도 저장할 수 없다.

## 3. 업체 구분별 날짜와 방식

### 최초실시

- 방문 필수다.
- 측정예정일 기준 working day `-3, -4, -5 ... -20` 순으로 탐색한다.
- `-20`을 넘는 과거일은 정상 자동결정으로 만들지 않는다.

### 타기관 신규

- 기존 확정 방식을 그대로 유지한다.
- 방문 필수다.
- primary는 working day `-20, -19 ... -3` 순으로 탐색한다.
- primary가 모두 hard constraint로 불가능할 때만 fallback `-25, -24 ... -21`을 검토한다.
- 경력 구성은 다른 사업장과 동일하게 §2의 자동결정 hard rule을 적용한다.

### 기존업체

- 유선이 기본이다.
- primary는 working day `-20, -19 ... -3`을 정책상 후보군으로 사용한다. 여러 기존업체를 배정할 때 `-20`부터 업체별로 첫 유효일을 고정해 같은 날짜에 몰아넣지 않는다.
- primary 안에서 hard constraint를 통과한 후보일을 대상으로 날짜별 기존업체 유선 배정 건수를 먼저 균등화한다. 아직 0건인 유효 후보일이 남아 있으면 이미 1건 이상 배정된 날짜에 두 번째 업체를 넣지 않는다.
- 날짜별 분산은 `0건 날짜 우선 → 모든 유효 날짜가 1건 이상이면 1건 날짜 우선 → 그 다음 2건 날짜 우선` 순으로 진행한다. 같은 날짜 건수가 같으면 `-20 → -19 → ... → -3` 순서를 tie-break로 사용한다.
- 날짜별 균등화는 기존 persisted·가확정 유선 plan과 이번 draft를 함께 합산한다. 업체 배열 순서나 코드 순서 때문에 특정 날짜에 몰리지 않아야 한다.
- 날짜 분산 규칙은 responsible의 1일 최대 3건 capacity와 별개다. 날짜 전체에 여러 responsible가 있더라도 유효한 빈 후보일이 남아 있으면 같은 날짜 중복을 먼저 만들지 않는다.
- primary가 모두 hard constraint로 불가능할 때만 fallback `-25, -24 ... -21`을 검토하며, fallback 안에서도 같은 날짜별 균등분산 원칙을 적용한다.
- 기존업체 때문에 별도 방문일을 만들지 않는다.
- 유선 파악은 실제 측정 업무와 병행할 수 있으므로 실제 측정 일정이 있다는 이유만으로 기존업체 유선 후보일을 제외하지 않는다.
- 이미 같은 날 필수 신규 방문이 있고 동일주소 또는 검증된 가까운 동선이며 방문 허용량과 후발 필수방문 여유를 해치지 않을 때만 선택 방문으로 올릴 수 있다.

### 공통 날짜 규칙

- 휴일·주말은 후보에서 제외한다.
- 측정예정일에서 역산한다. KST 오늘, 실행 시각, `candidate >= today` 조건으로 과거 후보를 제거하지 않는다.
- 날짜가 정책 범위에 있다는 것만으로 정상 선택으로 보지 않는다. 더 높은 우선순위 후보가 왜 탈락했는지 설명 가능해야 한다.
- 위 날짜·방식 규칙은 자동결정 기준이다. 관리자 수정 모달에서 다른 날짜·방식을 직접 지정하면 저장을 자동 적용으로 처리하지 않고 `운영지침 위반` 경고와 수동 override audit을 남긴다.

## 4. 2026-09-01 운영 전환과 측정자 고정형 역산 플래너

### 적용 범위

- 2026년 8월 실제 측정자료는 실운영 전 테스트·검증 자료다. 새 정책으로 다시 전체 계산하거나 일괄 backfill하지 않는다.
- 2026년 9월 1일 이후 실제 측정일을 실운영 적용 대상으로 한다.
- 9월 이후 측정대상의 정상 예비조사일이 8월에 해당하는 것은 허용한다. 적용 범위는 예비조사일이 아니라 실제 측정일을 기준으로 판정한다.
- 다일 사업장에서 2026년 8월과 9월 실제 측정일이 함께 존재하면 8월 assignment는 재계산하지 않는다. 공유 예비조사 plan을 변경하면 8월 기록 의미가 달라지는 경우 자동 적용하지 않고 `MANUAL_REQUIRED`로 넘긴다.

### 목적과 재사용 원칙

측정자 고정형 역산 플래너는 다음 계약을 가진다.

```text
사용자가 실제 측정일별 고정 측정자를 확정
→ 고정 측정자와 측정 참여자로 실제 측정팀 구성
→ 사업장 유형별 후보 날짜·방식 생성
→ 예비조사자 조합 생성
→ hard constraint와 실제 측정팀 정합성 검증
→ 선택한 실제 측정일의 전체 사업장을 batch 계산
→ AUTO_ASSIGNED / MANUAL_REQUIRED / SOURCE_INVALID 판정
→ Preview
→ 저장 직전 동일 validator 재실행
→ 원자 저장
```

- 플래너는 고정 측정자, 측정 참여자, 보고서 담당자, 실제 측정일을 변경하지 않는다.
- 한 사업장씩 코드 순서대로 선점하는 행별 탐욕 배정과 사후 보정 방식을 사용하지 않는다.
- 기본 실행 단위는 사용자가 선택한 실제 측정일의 전체 사업장이다.
- 선택 범위 밖의 사업장을 자동 변경하지 않지만, 후보일·직원·capacity·route에 영향을 주는 기존 plan과 보호값은 고정 점유로 읽는다.
- 현재 유효한 기존 plan이 새 hard constraint를 모두 통과하면 minimum-change 원칙으로 우선 보존한다.
- 찐확정·역사보호·관리자 수동보호 plan은 자동 변경하지 않는다.
- 향후 전체 배정 엔진은 측정자 후보안을 만든 뒤 이 플래너에 입력하여 예비조사까지 성립하는지 평가한다. 별도의 중복 예비조사 계산기를 만들지 않는다.
- 기존 V2 일반 자동추천은 OFF 상태를 유지한다. 사업장 상세 저장만으로 plan이나 측정자 확정값을 자동 생성하지 않는다.

## 5. 정상 자동결정, 실제 측정팀 정합성, 예외 판정

### 실제 측정팀 교집합 hard rule

정상 자동결정의 서류 정합성은 **예비조사자와 실제 측정팀의 교집합**으로 판정한다.

```text
실제 측정팀 = 고정 측정자 ∪ 해당 날짜 측정 참여자
```

- 단일일 측정은 `예비조사자 ∩ 실제 측정팀`에 한 명 이상이 있으면 정합성 조건을 충족한다.
- 고정 측정자가 예비조사자에 직접 포함되지 않아도, 같은 날 함께 이동하는 측정 참여자 중 한 명이 예비조사자에 포함되면 유효하다.
- 다일 측정은 전체 측정기간 중 최소 하루의 실제 측정팀과 예비조사자가 한 명 이상 일치하면 기간 단위 정합성 조건을 충족한다.
- 다일 정합성 판정은 `예비조사자 ∩ 모든 실제 측정일 실제 측정팀의 합집합`이 비어 있지 않은지로 계산한다.
- 보고서 담당자는 실제 측정팀에 명시적으로 포함된 경우에만 교집합 구성원이 된다. 보고서 담당자라는 이유만으로 match를 만들지 않는다.
- 교집합이 없는 후보는 날짜·경력·일정·용량이 모두 정상이어도 `AUTO_ASSIGNED` 후보가 아니다.

### 결정 상태

#### `AUTO_ASSIGNED`

- 원천 데이터가 유효하다.
- 고정 측정자가 사용자에 의해 명시적으로 확정되어 있다.
- 날짜·방식·경력·일정·용량·동선 hard constraint를 모두 통과한다.
- 예비조사자와 실제 측정팀의 교집합이 존재한다.
- 시스템이 선택 근거와 source fingerprint를 생성할 수 있다.

#### `MANUAL_REQUIRED`

원천은 계산 가능하지만 정상 자동안을 확정할 수 없는 경우다. 대표 사유는 다음과 같다.

- `FIXED_ASSIGNEE_NOT_CONFIRMED`: 해당 실제 측정일의 고정 측정자가 아직 확정되지 않음
- `ONLY_MISMATCH_ALTERNATIVES_AVAILABLE`: 교집합이 있는 안은 없고 불일치 대체안만 존재
- `NO_EXPERIENCED_PARTNER_AVAILABLE`: 비경력자와 조합할 유효 경력자가 없음
- `NO_VALID_PRELIMINARY_DATE`: 정상 날짜 후보가 없음
- `ROUTE_EVIDENCE_REQUIRED`: 복수 수행에 필요한 동선 근거가 없음
- `PROTECTED_PLAN_REQUIRES_REVIEW`: 보호 plan을 자동 변경해야만 정상안이 가능함
- `TRANSITION_BOUNDARY_REVIEW_REQUIRED`: 8월·9월 경계 다일 자료의 공유 plan 변경이 필요함

#### `SOURCE_INVALID`

계산 입력 자체가 불완전하거나 모순되어 신뢰할 수 없는 경우다. 대표 사유는 다음과 같다.

- 존재하지 않거나 식별할 수 없는 사업장·실제 측정일·사용자
- 날짜 형식 또는 다일 실제 측정일 구조 오류
- 활성 사용자·경력·공시료 base code 원천의 모순
- 동일한 원천을 서로 다른 사용자 또는 날짜로 해석해야 하는 충돌
- snapshot 또는 baseline을 완전하게 구성할 수 없음

### 불일치 대체안 — 방안 B

- 교집합이 있는 정상 후보를 모든 날짜·허용 조합에서 탐색한 뒤에도 찾지 못한 경우에만 불일치 대체안을 계산한다.
- 불일치 대체안은 날짜·경력·일정·용량 등 다른 규칙을 통과하더라도 `MANUAL_REQUIRED`의 참고자료다.
- 불일치 Preview에는 자동 적용 버튼을 제공하지 않는다. 일반 일괄 적용 대상에도 포함하지 않는다.
- 관리자가 불가피한 실제 업무 예외라고 판단하면 별도의 관리자 수동수정 경로에서만 저장할 수 있다.
- 관리자 불일치 override는 구체적인 경고, 예외 사유, 변경 전후값, 실제 측정팀, 예비조사자, 변경자, 변경시각과 관련 planner run을 audit에 남긴다.
- 관리자 override 결과는 `AUTO_ASSIGNED`로 바꾸지 않고 `MANUAL_OVERRIDE` 출처로 구분한다. 정상 자동배정 통계와 Golden Regression 정답에 섞지 않는다.
- 관리자 override plan은 사용자가 명시적으로 자동 재계산 범위에 다시 포함하기 전까지 고정 점유값으로 취급한다.

## 6. 결정론적 계산 순서 — hard constraint와 preference 분리

### 계산 순서

1. 현재 활성 측정대상, 실제 측정일, 사업장 구분을 확정한다.
2. 실제 측정일별 고정 측정자 확인 기록과 측정 참여자를 읽어 실제 측정팀을 구성한다.
3. 보고서 담당자, 경력정보, 직원 불가 일정, 기존 plan, 보호 상태, capacity, route snapshot을 포함한 원천 snapshot을 만든다.
4. 원천 무결성을 검사하고 `SOURCE_INVALID` 대상을 분리한다.
5. 사업장 유형별 날짜와 방식 후보를 만든다.
6. 경력자 단독 및 경력자+비경력자 후보 조합을 만든다.
7. 날짜·방식·경력·직원 일정·capacity·route·보호 상태 hard constraint를 검사한다.
8. 예비조사자와 실제 측정팀의 교집합이 없는 후보를 정상 자동후보에서 제거한다.
9. 선택한 실제 측정일의 전체 사업장을 대상으로 날짜·인력 공유자원을 함께 계산한다.
10. hard constraint를 통과한 완성안끼리 preference를 순서대로 비교한다.
11. 각 대상의 판정, 선택 근거, 탈락 사유와 mismatch 대안을 생성한다.
12. Preview를 반환하며 DB를 변경하지 않는다.
13. 적용 직전 동일 원천과 validator를 다시 실행한다.
14. source·baseline·보호 상태가 같을 때만 영향 범위를 원자 저장한다.

### Hard constraint

- 사업장·실제 측정일·사용자 원천 무결성
- 고정 측정자 명시적 확정
- 사업장 유형별 날짜와 방문·유선 방식
- 휴일·주말 제외와 측정예정일 기준 역산
- 최소 1명의 경력자와 비경력자 단독 금지
- 방문 수행자 전원의 불가 일정·실제 측정 일정·방문 capacity
- 기존업체 유선 responsible의 불가 일정·유선 capacity
- 실제 측정팀 교집합
- 동일주소·검증된 차량 동선 등 필요한 route evidence
- 찐확정·역사보호·관리자 수동보호 경계
- 다일 assignment의 날짜별 독립성과 carry-forward 금지

### Preference

아래 순서는 hard constraint를 통과한 후보끼리만 비교한다.

1. 현재 정상인 기존 plan의 minimum-change 보존
2. primary 날짜 사용과 fallback 최소화
3. 기존업체 지정 경력 reviewer 조합
4. 보고서 담당자와 업무상 가능한 예비조사 조합
5. 기존업체 유선 날짜 균등분산
6. 예비조사표 작성자별 작성 건수 균등
7. 같은 조건에서 동일주소와 더 짧은 실제 차량 동선
8. 날짜·사용자 ID·사업장 stable ID의 안정적인 tie-break

- 보고서 담당자 preference나 작성 업무 균등을 위해 hard constraint를 깨지 않는다.
- 하나의 임의 가중치 합계로 정책 우선순위를 뒤집지 않는다. 우선순위를 순차 비교하는 lexicographic 방식으로 결정한다.
- 동일 snapshot, 동일 canonical version, 동일 planner version이면 입력 배열 순서와 관계없이 동일 결과를 반환해야 한다.
- DB 조회 순서, 화면 정렬, 객체 삽입 순서, 난수에 따라 결과가 바뀌면 FAIL이다.

## 7. 조사량·용량·직원 불가 일정과 이동

### 방문 예비조사

- 하루 1건이 원칙이다.
- 동선이 명확히 적합할 때 최대 2건까지 자동결정할 수 있다.
- 같은 직원의 기존 manual·가확정 방문, 영향 범위 밖 유지 방문, 새 draft 방문을 모두 합산한다.
- 실제 vehicle route 30분 이하는 same-route로 적극 우선한다.
- 31~60분은 더 적합한 단독 날짜가 없을 때 fallback 검토 범위다.
- 60분 초과는 같은 날 묶지 않는다.
- route evidence가 없으면 동일주소 외 자동 근거리 판정을 확정 근거로 사용하지 않는다.
- 경력자+비경력자 방문은 두 사람 모두 실제 수행자다. 경력자가 작성 카운터에서 제외되더라도 일정·방문 capacity·동선 검사에서는 제외하지 않는다.

### 기존업체 유선

- 실제 유선 수행자는 responsible 1명이다.
- 경력자 단독이면 해당 경력자가 responsible이자 예비조사표 작성자다.
- 경력자+비경력자이면 비경력자가 responsible이자 예비조사표 작성자이고, 경력자는 reviewer다.
- 기존업체 유선에서 비경력 responsible별 우선 경력 reviewer 조합은 다음과 같다.

| 비경력 responsible | 우선 경력 reviewer | 화면 표시 |
|---|---|---|
| 강종구 | 이태환 | 이태환, 강종구 |
| 고유빈 | 이주형 | 이주형, 고유빈 |
| 김민영 | 한기문 | 한기문, 김민영 |

- 위 표는 preference다. hard constraint나 실제 측정팀 교집합을 충족하지 못하면 다른 유효 경력자를 탐색한다.
- 보고서 담당자 조합 preference도 실제 측정팀 교집합과 hard constraint를 통과한 후보에만 적용한다.
- 다일에서 날짜별 보고서 담당자가 다르면 각 날짜 원천을 모두 보존하며 한 날짜의 담당자를 다른 날짜에 덮어쓰지 않는다.
- 동일 예비조사일·동일 responsible 기준 자동결정은 1인당 최대 3개다.
- 날짜 선택은 유효한 0건 날짜부터 `0 → 1 → 2` 순환으로 균등분산한다.
- reviewer는 유선 3건 capacity, responsible 균등배정, 날짜별 유선 배정 건수와 예비조사표 작성자 카운터에 포함하지 않는다.
- 기존업체 유선은 실제 측정 업무와 병행 가능하므로 responsible 또는 reviewer의 실제 측정 일정 자체를 유선 후보일 hard block으로 사용하지 않는다.
- 정상 데이터에서 기존업체 유선 추천일 `null`을 정상 PASS로 인정하지 않는다. 모든 후보일이 responsible의 명시적 불가 일정 또는 이미 찬 유선 capacity로 막힌 사실이 입증된 경우에만 `MANUAL_REQUIRED`로 남긴다.

### 직원 불가 일정

- `user_schedule_blocks`는 실제 수행자의 명시적 불가 일정 원천이다.
- 방문 예비조사는 현장 수행자 전원에게 적용한다.
- 기존업체 유선은 전화 파악 responsible에게만 동일일 hard block으로 적용한다. reviewer는 동일일 유선 수행량을 소비하지 않는 검수 역할이므로 유선 후보일 hard block 대상으로 사용하지 않는다.
- 고정 측정자 확정과 실제 측정팀 검증에는 해당 실제 측정일의 기존 불가 일정 정책을 적용한다.
- 불가 일정은 균등배정, 동일주소, 동선 preference보다 우선하는 hard constraint다.
- 계획 생성 후 불가 일정이 추가되면 가확정은 `재검토 필요`로 표시하고, 찐확정은 자동 변경하지 않는다.
- 관리자가 불가 일정 직원 등을 직접 지정하는 경우 경고와 audit을 남기되 관리자 수동 override 정책을 따른다.

### 실제 측정팀과 이동

- 측정 참여자는 실제 측정일에 고정 측정자와 함께 이동하는 인력으로 계산한다.
- 같은 직원이 같은 실제 측정일에 여러 사업장의 실제 측정팀에 포함되면 고정 측정자 여부와 관계없이 해당 사업장들의 동일주소·차량 동선과 실제 수행 가능성을 검증한다.
- 공시료 담당자만 다르다는 이유로 측정 참여자의 중복 이동 충돌을 무시하지 않는다.
- 실제 측정팀의 이동 가능성 판단에도 동일주소 또는 검증된 route snapshot을 사용한다. 근거가 없으면 자동으로 가능하다고 추정하지 않는다.
- 측정 참여자는 공시료 담당자 배정 건수와 `A/AA`, `C/CC` 반복코드 카운트에는 포함하지 않는다. 그 카운트는 고정 측정자에게만 적용한다.

## 8. 측정자(공시료)와 코드

고정 base code:

| 측정자 | base code |
|---|---|
| 이태환 | A |
| 한기문 | B |
| 강종구 | C |
| 이주형 | D |
| 고유빈 | F |
| 김민영 | G |

동일 실제 측정일·동일 측정자의 배정 수에 따라 base를 반복한다.

- 1건: `C`
- 2건: `C`, `CC`
- 3건: `C`, `CC`, `CCC`
- 관리자 수동수정으로 4건 이상을 명시적으로 선택한 경우에도 `CCCC`처럼 base를 배정 수만큼 반복해 날짜 그룹 전체를 정규화하고 지침 초과 경고와 audit을 남긴다.

A/B/D/F/G도 동일하게 적용한다.

- 코드는 해당 실제 측정일의 동일 담당자 assignment 그룹에서 정규화되는 값이다. 특정 사업장에 base code를 영구 고정하지 않는다.
- 같은 날 강종구가 2개 사업장을 맡으면 한 사업장은 `C`, 다른 사업장은 `CC`다. 어느 사업장에 어떤 코드를 줄지는 안정적인 정규화 순서로 결정한다.

### 사업장별·측정일별 assignment

- 공시료 배정 단위는 `실제 측정일 × 사업장` 1건이다.
- 같은 사업장이라도 실제 측정일이 여러 날이면 각 날짜마다 assignment를 1건씩 가진다.
- 한 assignment를 여러 사업장에 공동으로 쓰거나 이전 날짜 값을 다음 날짜에 복사하지 않는다.
- 같은 날짜의 담당자 또는 사업장 집합이 바뀌면 영향받는 해당 날짜 assignment 그룹 전체를 다시 정규화한다.
- 앞선 날짜의 `C`, `CC` 코드 순서를 다음 측정일로 carry-forward하지 않는다.

### 고정 측정자와 향후 전체 배정 엔진

- 현재 측정자 고정형 역산 경로는 사용자가 확정한 측정자를 변경하거나 새로 자동배정하지 않는다.
- 향후 전체 배정 엔진은 실제 측정일의 모든 사업장을 동시에 보고 1인·1일·1업체·1공시료 1차 순환을 우선한다.
- 같은 우선 후보군에 아직 당일 0건인 배정 가능자가 있으면 이미 1건을 받은 사람에게 두 번째 업체를 배정하지 않는다.
- 두 번째 업체는 1차 순환으로 전체 배정이 불가능할 때만 실제 동선을 검증하여 검토한다.
- 자동결정의 정확히 3건은 관리자가 실제 수행 가능성을 검토한 명시 예외에서만 허용한다.
- 자동결정 4건 이상은 허용하지 않는다.
- 위 자동 한도는 관리자 수정 모달의 직접 수동지정 한도와 구분한다. 관리자가 지침 초과 값을 직접 저장하면 경고·확인·audit과 날짜 그룹 코드 재정규화를 적용한다.
- 향후 전체 배정 엔진이 만든 각 측정자 후보안은 반드시 측정자 고정형 역산 플래너를 통과하여 실제 측정팀 교집합이 있는 예비조사 plan을 만들 수 있어야 정상안이 된다.

## 10. 기준 데이터 흐름, 결과 근거와 표시

기준 흐름은 다음과 같다.

`measurement_target_business → 고정 측정자 확인 → 역산 planner draft → 예비조사 plan/assignment → measurement_journal`

- 현재 target이 존재하면 측정일지 검색도 target의 유효 측정일과 lifecycle(`실시`)을 따른다.
- `미실시`·`거래종료` target에 연결된 과거 journal row는 삭제하지 않지만 현재 검색·표시에서는 제외한다.
- target 자체가 없는 순수 과거 이력은 이 기준으로 삭제하거나 수정하지 않는다.
- 예비조사 계획과 목록의 기본 표시 순서는 측정대상 사업장 관리의 canonical 기본 조회순서(상태 → 예정월 → 코드)를 공유한다.
- 예비조사자 복수 표시는 항상 경력자를 먼저, 비경력자를 뒤에 표시한다.
- 날짜별 목록의 `측정자(공시료)` 칸은 해당 조회일의 실제 assignment를 `이름(코드)`로 표시한다.
- 다일 전체 날짜별 공시료 내역은 상세 화면에서 확인하고 날짜별 목록 셀에 다른 날짜 assignment를 병합하지 않는다.
- 실제 측정팀은 고정 측정자와 측정 참여자를 역할별로 구분하여 확인할 수 있어야 한다.
- `AUTO_ASSIGNED`는 사용자가 규칙을 다시 계산해야 한다는 뜻이 아니다. 시스템이 hard constraint와 정합성을 검증한 결과다.
- `MANUAL_REQUIRED`는 값 없이 구체적인 사유와 필요한 경우 불일치 대체안을 표시한다.
- `SOURCE_INVALID`는 원천 수정이 필요함을 명확히 표시하고 임의 값을 만들지 않는다.

### 설명 가능한 계산 기록

각 planner run은 최소 다음 근거를 보존한다.

- planner run ID, planner version, canonical rule version
- mutation scope와 constraint universe 식별값
- source snapshot fingerprint와 기존 baseline digest
- 고정 측정자 확인 정보와 실제 측정팀
- 선택한 날짜·방식·예비조사자·예비조사표 작성자
- hard constraint 통과·탈락 reason code
- 실제 측정팀 교집합 근거
- route evidence 식별값
- preference 비교 결과와 안정적 tie-break
- 최종 결정 상태와 값의 출처(`ENGINE`, `MANUAL_OVERRIDE`, `PRESERVED`)

평상시 화면에는 `규칙 검증 완료`, `수동 결정 필요`, `원천 수정 필요`처럼 간단히 표시하고 상세 근거는 관리자·개발자 audit에서 확인한다.

### 수정 모달 표시

- 수정 모달 헤더는 `예비조사 상세`로 고정하고 업체명은 본문 상단에 `업체명 : {사업장명}` 형식으로 표시한다.
- 긴 업체명은 줄바꿈되어 모달 폭을 넘지 않아야 한다.
- 헤더 닫기 아이콘과 별개로 하단에 명확한 `닫기` 버튼을 제공한다.
- 관리자 수동 저장 성공 후 이전 planner draft가 새 DB 값을 덮어 표시해서는 안 된다. 관련 draft를 폐기하고 DB를 재조회한다.

## 11. 찐확정과 repair

- `measurement_journal` row가 존재하면 찐확정이다.
- `sequence_number`는 찐확정 판정 기준으로 사용하지 않는다.
- 찐확정은 자동추천·자동재추천·자동삭제·자동 역산 변경 대상에서 제외한다.
- 찐확정도 현행 날짜 정책과 실제 측정팀 정합성 비교 결과를 표시할 수 있으나 자동 변경하지 않는다.
- 관리자 또는 예비조사 담당자의 기존 repair 경로는 계속 사용할 수 있다.
- 관리자는 수정 모달에서 찐확정 여부와 관계없이 예비조사일·방식·예비조사자·날짜별 측정자를 직접 수정할 수 있다. 이는 관리자 전용 수동 override로 처리한다.
- 관리자 직접수정은 `measurement_journal`을 삭제·재생성하거나 측정예정일·측정 참여자·보고서 담당자를 연쇄 변경하지 않는다.
- 관리자 직접수정이 운영지침을 벗어나면 구체적인 경고, 예외 사유, 명시 확인과 before/after audit을 남긴다.
- 예비조사 담당자 권한만 있는 사용자는 찐확정에 대해 기존 repair 경로와 보호 규칙을 따른다.
- 과거 당시의 불가 일정·용량·route를 재현할 수 없는 과거값은 자동 위반으로 단정하지 않고 수동 검토 대상으로 처리한다.

### 측정 참여자·보고서 담당자 source repair

- 측정 참여자와 보고서 담당자는 서로 독립적으로 보정한다.
- 일반 예비조사 수동수정은 코드, 사업장명, 구분, 실제 측정일, 측정 참여자, 보고서 담당자를 자동 변경하지 않는다.
- 이 원천들은 별도 source repair 기능에서 사용자가 명시적으로 선택한 필드만 수정한다.
- 선택하지 않은 역할, 측정일지와 과거 row는 변경하지 않는다.
- before/after, 사유, 수정자를 audit에 남긴다.

## 12. 수동 수정·재계산·삭제

### 자동결정·일반 권한 경로

- 관리자 또는 `users.is_preliminary_survey_manager = true`가 역산 Preview, 적용, 일반 repair를 수행한다.
- 일반 사용자는 조회 중심이다.
- 비찐확정 plan과 고정 측정자 확인값의 일반 수정은 권한과 source stale 검사를 통과해야 한다.
- 예비조사 담당자만으로 찐확정 보호나 관리자 전용 예외를 우회할 수 없다.

### 관리자 수정 모달 — 최종 수동판단

- 관리자(`role = 관리자`) 수정 모달은 실제 업무 예외를 반영하는 최종 수동수정 화면이다.
- 관리자는 찐확정 여부와 관계없이 예비조사일, 방식, 예비조사자, 유선 responsible/reviewer, 실제 측정일별 측정자를 직접 수정할 수 있다.
- 다일 사업장은 실제 측정일별 측정자를 독립 선택한다.
- 날짜범위, 방식, 경력조합, 불가 일정, 용량, 실제 측정팀 교집합, 1일 권장 건수 등 지침 위반 사항을 구체적으로 표시한다.
- 지침 위반만으로 관리자 수동 저장 버튼을 비활성화하지 않지만 경고 확인과 예외 사유를 요구한다.
- `ONLY_MISMATCH_ALTERNATIVES_AVAILABLE` Preview에서 바로 적용하지 않는다. 관리자가 별도 수동수정 화면으로 진입하여 다시 확인해야 한다.
- 관리자 측정자 직접수정 후에는 같은 실제 측정일의 이전·신규 담당자 그룹 전체 코드를 원자적으로 재정규화한다.
- 관리자 직접수정은 관리자 전용 서버 RPC·transaction 안에서만 찐확정 guard를 제한적으로 bypass한다.
- 존재하지 않는 target·사용자, 권한 위조, 날짜 구조 오류, stale source, 동시성 충돌, transaction 실패 등 구조적 오류는 저장을 차단한다.
- 관리자 수정 전후 plan·assignment·실제 측정팀·지침 경고·예외 사유·수정자·수정시각을 audit에 남긴다.

### 공통

- 기존 V2 일반 자동추천은 OFF 상태를 유지한다.
- 사업장 상세 저장만으로 고정 측정자 확인, 역산 실행 또는 plan 적용을 자동 수행하지 않는다.
- 기존 manual plan은 새 hard constraint를 통과하는 경우에만 minimum-change 대상으로 보존한다.
- 업체별 재계산은 같은 예비조사일의 조사자 조합, 방문·유선 capacity, 동일주소·방문 묶음, 같은 실제 측정일의 실제 측정팀과 assignment 그룹을 dependency closure로 확장한다.
- 찐확정·역사보호·관리자 수동보호값은 dependency 계산에는 포함하되 자동 변경 대상에서는 제외한다.

### V2 plan 안전 삭제

- 찐확정되지 않은 persisted V2 plan은 예비조사 담당자 또는 관리자가 삭제할 수 있다.
- 삭제 대상은 `preliminary_survey_v2_plans`와 해당 plan에 귀속된 `preliminary_survey_v2_measurement_assignments`다.
- `measurement_target_business`, 실제 측정일, `measurement_journal`, legacy 원천은 삭제하지 않는다.
- true-confirmed plan과 legacy reconciliation 또는 historical recovery 추적 plan은 일반 삭제할 수 없다.
- 삭제 후 영향을 받는 assignment 그룹은 같은 transaction에서 재정규화한다.

## 13. 저장·동시성·보안 불변식

- 측정자(공시료)의 authoritative source는 `preliminary_survey_v2_measurement_assignments`다.
- 고정 측정자 여부는 별도의 사용자 확인 기록으로 식별한다. 기존 assignment 존재만으로 자동 확정하지 않는다.
- 과거 `recommendation_reason.measurementAssignee`는 read-only 표시 fallback일 뿐 새 write·고정 확인·자동 backfill 근거로 사용하지 않는다.
- Preview 생성은 DB를 변경하지 않는다.
- plan과 날짜별 assignment는 최종 wrapper RPC 한 transaction에서 저장한다.
- apply 서버는 현재 원천으로 실제 측정팀과 예비조사 plan을 다시 계산하고 canonical draft, source fingerprint, 기존 baseline을 비교한다.
- 클라이언트가 보낸 사용자 ID·이름·공시료 코드·판정 boolean을 authoritative 판단 근거로 신뢰하지 않는다.
- 같은 실제 측정일, 후보 예비조사일과 관련 직원의 영향 그룹은 advisory lock 또는 row lock으로 직렬화한다.
- 고정 측정자, 측정 참여자, 보고서 담당자, 실제 측정일, 경력, 불가 일정, 기존 plan, 보호 상태, route snapshot 중 하나라도 Preview 이후 달라지면 `SOURCE_CHANGED`로 0건 저장하고 새 계산을 요구한다.
- 찐확정 guard는 plan·assignment의 INSERT·UPDATE·DELETE에서 OLD와 NEW target을 모두 검사한다.
- 관리자 수동수정만 관리자 전용 서버 RPC에서 제한적으로 guard를 우회하며 일반 경로·클라이언트 직접 호출은 우회하지 않는다.
- 관리자 전용 RPC도 서버 권한 재확인, append-only audit, lock, stale 검사와 transaction rollback을 수행한다.
- 이미 적용된 migration을 수정하지 않고 forward-only migration으로 변경한다.
- 운영 적용 전 비운영 DB에서 migration·RPC·rollback·권한·동시성·stale·route evidence를 검증한다.

- 9월 이후 대상의 정상 예비조사일이 8월인 것은 이 보호 규칙의 위반이 아니다.

## 15. 회귀 검증 사례

아래 사례는 정책을 구현·검증할 때 사용하는 회귀 fixture다. 실제 운영일정이 변하면 날짜는 다시 계산할 수 있으나 검증하려는 역할 규칙을 임의로 바꾸지 않는다.

### 2026-08-31 측정예정 6개 사업장 역할 사례

| 코드 | 예비조사자 | 유선 responsible | 경력 reviewer | 측정자(공시료) | 경력 구성 |

- 이 표는 8월 Production 값을 다시 만들기 위한 목표표가 아니라 역할·작성자·유선 책임 구조를 검증하는 테스트 fixture다.
- 공시료 코드는 해당 날짜에 각 담당자가 이 사업장 1건만 맡는 조건의 base 예시이며 특정 사업장에 영구 고정하지 않는다.
- 비경력자 단독 자동결정이 없어야 한다.
- 경력자+비경력자 유선은 비경력자 responsible·예비조사표 작성자, 경력자 reviewer로 해석한다.
- 경력자+비경력자 작성 카운터에서는 비경력자만 1건 증가하고 경력자는 증가하지 않는다.
- 경력자 단독은 해당 경력자가 예비조사표 작성자이며 작성 카운터가 1건 증가한다.
- 복수 표시 순서는 경력자, 비경력자이지만 표시 순서로 responsible를 판정하지 않는다.
- 기존업체 유선 6건에 유효한 primary 후보일이 6일 이상 있으면 먼저 서로 다른 날짜에 분산한다.

### 필수 Golden Regression

- `고정 측정자 확인`: 기존 assignment가 있어도 사용자 확인 기록이 없으면 `FIXED_ASSIGNEE_NOT_CONFIRMED`다.
- `측정 참여자 match`: 고정 측정자와 예비조사자가 다르더라도 측정 참여자 중 한 명이 예비조사자이면 `AUTO_ASSIGNED` 정합성이 성립한다.
- `교집합 없음`: 실제 측정팀 누구도 예비조사자에 없으면 자동 적용하지 않고 `ONLY_MISMATCH_ALTERNATIVES_AVAILABLE` 또는 다른 `MANUAL_REQUIRED` 사유를 반환한다.
- `관리자 mismatch override`: 불일치 Preview에 직접 적용 버튼이 없어야 하며 별도 관리자 수동수정에서만 사유·경고·audit 후 저장한다.
- `보고서 담당자 보호`: 역산 결과로 보고서 담당자 또는 측정 참여자를 변경하지 않는다.
- `작성자 균등`: 경력자+비경력자 조합의 경력자는 작성 카운터에서 제외하지만 방문 capacity와 일정에서는 제외하지 않는다.
- `batch 결정론`: 선택한 실제 측정일의 사업장·사용자 배열 순서를 섞어도 결과가 동일하다.
- `기존 plan 보존`: 새 hard constraint를 통과하는 기존 plan은 불필요하게 변경하지 않는다.
- `8월 보호`: 8월 실제 측정대상에 신규 일괄 plan·assignment를 만들지 않는다.
- `9월 대상의 8월 예비조사일`: 9월 실제 측정대상의 정상 8월 예비조사 후보를 현재보다 과거라는 이유로 제외하지 않는다.
- `H0508 다일`: 예비조사 plan은 공유하고 날짜별 실제 측정팀·측정자·공시료 코드는 독립 처리하며 carry-forward하지 않는다. 전체 기간 중 최소 하루 실제 측정팀과 예비조사자가 일치하면 정합성 조건을 충족한다.
- `H0525`: 최초실시 날짜 범위 `-3 ... -20`을 지킨다.
- `H0526`: 최초실시는 방문이어야 한다.
- `H0527`: 실제 측정팀 교집합과 hard constraint를 통과한 후보 안에서 보고서 담당자 조합 preference를 적용한다.
- `H0050 + H0527`: 같은 실제 측정팀 구성원이 서로 이동 불가능한 사업장에 중복 연결되면 코드·사업장 순서로 억지 배정하지 않는다.
- `C/CC 정규화`: 같은 날짜 동일 담당자 두 사업장은 `C`, `CC`처럼 날짜 그룹 전체를 결정론적으로 정규화한다.
- `SOURCE_CHANGED`: Preview 후 고정 측정자·측정 참여자·보고서 담당자·일정·route가 바뀌면 0건 저장한다.
- 관리자 저장 후 이전 draft가 새 DB 값을 덮어 표시하면 FAIL이다.
- 수정 모달 헤더의 긴 업체명이 닫기 버튼을 밀어내면 FAIL이다.

## 16. 운영지침 변경 절차

업무 규칙 변경 시 다음 순서를 지킨다.

1. 사용자가 최종 결정한 내용을 이 문서에 먼저 반영한다.
2. 문서 전체에서 새 결정과 충돌하는 과거 문구를 전수 검색해 삭제한다. 과거 규칙은 Git 이력으로 추적한다.
3. 실제 사용자 예시가 있다면 회귀 fixture로 고정할지 검토한다.
4. `BUSINESS_LOGIC.md`, `project_rules.md`, `AGENTS.md` 등 상위 안내 문서에 중복·충돌하는 예비조사 규칙이 없는지 확인한다.
5. 그 다음 코드·DB·테스트를 이 문서에 맞춘다.
6. Fresh verifier는 코드가 현재 문서를 구현했는지 독립 검증한다.

문서와 코드가 충돌하면 구현을 임의로 정답으로 간주하지 않는다.
