# 예비조사 업무 규칙

> 현행 통합본: 2026-08-31  
> 정책 기준: 2026-08-30까지 사용자가 최종 확정하고 2026-08-31 재확인한 업무 규칙

이 문서는 예비조사 기능의 **단일 장기 기준 문서(canonical business rule)**다. 과거 커밋, 코드 주석, 이전 작업지시서, 테스트가 이 문서와 충돌하면 현행 통합본을 우선한다. 새 업무 결정을 내리면 먼저 이 문서를 갱신하고, 이후 코드·DB·테스트를 이 기준에 맞춘다.

예비조사 추천의 날짜 기준점은 현재 날짜가 아니라 **측정예정일**이다. 정책 범위의 정상 후보를 현재보다 과거라는 이유만으로 제외하지 않는다.

## 1. 역할과 authoritative source

- 사업장 상세가 실제 업무 입력의 시작점이다. 사용자는 측정예정일, 보고서 담당자, 날짜별 측정 참여자와 다일 일정을 먼저 계획한다.
- **예비조사자**는 페이퍼상 예비조사를 수행하는 사람 또는 조합이다.
- **측정자 = 메인측정자 = 공시료 담당자**는 같은 역할이다.
- **측정 참여자**는 실제 현장 참여자다. 단일일은 `measurement_target_business.collaborators`, 다일은 해당 날짜의 `daily_staff[].collaborators`가 원천이다.
- **보고서 담당자**는 보고서 작성·관리 담당자다. 사업장 단위 기본 원천은 `measurement_target_business.measurer_id`, 다일의 날짜별 값은 해당 `daily_staff[].measurer_id`를 따른다.
- 측정 참여자의 배열 순서와 보고서 담당자 포함 여부는 측정자(공시료) 역할을 뜻하지 않는다.
- 예비조사 화면에서 측정 참여자·보고서 담당자를 임의 추론하거나 예비조사자/측정자 값에서 역산하지 않는다.
- `daily_staff.measurer_id`를 공시료 담당자로 해석하거나 `daily_staff.collaborators`의 순서로 메인 역할을 추론하지 않는다.

## 2. 예비조사 경력 구성 — 모든 사업장 공통 hard rule

경력 여부는 `users.is_preliminary_survey_experienced`만 사용하며 입사일 등으로 추론하지 않는다.

| 예비조사자 구성 | 허용 여부 |
|---|---|
| 경력자 단독 | 허용 |
| 경력자 + 비경력자 | 허용 |
| 경력자 + 경력자 | 수동 선택 시 사용자 확인 후 허용 |
| 비경력자 단독 | **금지** |

- 모든 사업장 유형과 모든 방식(방문/유선)에 동일하게 적용한다.
- 예비조사자 조합에는 **최소 1명의 경력자가 반드시 포함**되어야 한다.
- 경력자+비경력자 조합에서는 **비경력자를 페이퍼 작성 책임자로 둘 수 있다.** 경력자는 같은 예비조사자 조합의 경력자 역할을 맡는다.
- 경력자를 붙일 수 없는 날짜에 비경력자만 남는다면 `경력 검토자 미배정` 경고로 추천을 살려두지 않는다. **그 날짜 후보를 탈락시키고 다음 후보일을 탐색한다.**
- 경력자 2명 이상 조합은 자동추천의 기본 조합이 아니다. 사용자가 수동으로 선택한 경우 기존 확인 절차를 거쳐 허용한다.

## 3. 업체 구분별 날짜와 방식

### 최초실시

- 방문 필수.
- 측정예정일 기준 working day `-3, -4, -5 ... -20` 순으로 탐색한다.
- `-20`을 넘는 과거일은 정상 추천으로 만들지 않는다.

### 타기관 신규

- **기존 확정 방식을 그대로 유지한다.**
- 방문 필수.
- primary는 working day `-20, -19 ... -3` 순으로 탐색한다.
- primary가 모두 hard constraint로 불가능할 때만 fallback `-25, -24 ... -21`을 검토한다.
- 경력 구성은 다른 사업장과 동일하게 §2의 공통 hard rule을 적용한다.

### 기존업체

- 유선이 기본이다.
- primary는 working day `-20, -19 ... -3` 순으로 탐색한다.
- primary가 모두 hard constraint로 불가능할 때만 fallback `-25, -24 ... -21`을 검토한다.
- 기존업체 때문에 별도 방문일을 만들지 않는다.
- 이미 같은 날 필수 신규 방문이 있고 동일주소 또는 검증된 가까운 동선이며 방문 허용량과 후발 필수방문 여유를 해치지 않을 때만 선택 방문으로 올릴 수 있다.

### 공통 날짜 규칙

- 휴일·주말은 후보에서 제외한다.
- 측정예정일에서 역산한다. KST 오늘, 실행 시각, `candidate >= today` 조건으로 과거 후보를 제거하지 않는다.
- 날짜가 정책 범위에 있다는 것만으로 정상 선택으로 보지 않는다. 더 높은 우선순위 후보가 왜 탈락했는지 설명 가능해야 한다.

## 4. 추천 계산 순서 — hard constraint 우선

강한 제약을 먼저 해결하고 통과한 후보에 대해서만 soft preference를 계산한다.

1. 현재 활성 측정대상과 사업장 구분을 확정한다.
2. 사업장 유형에 따라 방식과 날짜 후보 순서를 만든다.
3. 각 후보일에서 예비조사 경력 구성 hard rule을 검사한다.
4. 예비조사자 전원의 직원 불가 일정과 실제 측정 일정 충돌을 검사한다.
5. 방문/유선 용량과 기존 plan·영향 범위 dependency를 검사한다.
6. 방문이면 동일주소·실제 vehicle route 등 필수 동선 조건을 검사한다.
7. 위 hard constraint를 통과한 첫 날짜와 예비조사자 조합을 확정한다.
8. 그 다음에 측정자(공시료) 균등배정과 예비조사자↔공시료 soft preference를 계산한다.
9. stale/lock/찐확정/assignment hard max를 최종 재검증한다.
10. 임시 draft를 사용자에게 보여주고 확인 후 적용한다.

- 공시료 정합성이나 코드 순서 때문에 경력·일정·용량 hard rule을 깨지 않는다.
- 추천 생성은 임시 draft만 만들고 DB를 변경하지 않는다.
- 저장 직전 원천값, baseline, hard constraint가 달라지면 다른 안을 자동 저장하지 않고 재검토를 요구한다.

## 5. 조사량·용량·직원 불가 일정

### 방문

- 하루 1건이 원칙이다.
- 동선이 명확히 적합할 때 최대 2건까지 자동추천할 수 있다.
- 같은 직원의 기존 manual/가확정 방문, 영향 범위 밖 유지 방문, 새 추천 방문을 모두 합산한다.
- 실제 vehicle route 30분 이하는 same-route를 적극 우선한다.
- 31~60분은 더 적합한 단독 날짜가 없을 때의 fallback 검토 범위로 둔다.
- 60분 초과는 같은 날 묶지 않는다.
- route evidence가 없으면 동일주소 외 자동 근거리 판정을 확정 근거로 사용하지 않는다.

### 유선

- 동일 예비조사일·동일 responsible 기준 1인당 최대 3개다.
- 복수 예비조사자의 경력자 역할 자체를 별도 유선 수행 건수로 중복 계산하지 않는다.
- 단, 조합에 포함된 모든 예비조사자는 해당 날짜의 직원 불가 일정 및 실제 측정 충돌을 통과해야 한다.

### 직원 불가 일정

- `user_schedule_blocks`는 공통 불가 일정 원천이다.
- 등록된 날짜에는 해당 직원을 예비조사자, 측정자(공시료), 측정 참여자, 보고서 담당자로 새 배정하지 않는다.
- 불가 일정은 공시료 균등배정, 동일주소, 동선, 관리자 3건 예외보다 우선하는 hard constraint다.
- 계획 생성 후 불가 일정이 추가되면 가확정은 `재검토 필요`로 표시한다. 찐확정은 자동 변경하지 않고 관리자 repair 또는 사용자 판단 대상으로 남긴다.

## 6. 측정자(공시료)와 코드

고정 base code:

| 측정자 | base code |
|---|---|
| 이태환 | A |
| 한기문 | B |
| 강종구 | C |
| 이주형 | D |
| 고유빈 | F |
| 김민영 | G |

동일 측정일·동일 측정자의 배정 수에 따라 base를 반복한다.

- 1건: `C`
- 2건: `C`, `CC`
- 3건: `C`, `CC`, `CCC`

A/B/D/F/G도 동일한 방식으로 적용한다.

### 자동 한도와 관리자 예외

- 1인 동일일 1~2건까지 자동추천한다.
- 정확히 3건은 동일주소·가까운 동선 등 실제 수행 가능성을 **관리자가 직접 검토한 명시 예외**에서만 허용한다.
- 예비조사 담당자 권한만으로 3건 예외를 승인할 수 없다.
- 4건 이상은 승인 여부와 관계없이 hard block한다.
- 3건 관리자 예외 단위는 `measurement_date + assignee_user_id + sorted target_ids`의 canonical fingerprint다. 날짜·담당자·업체 집합이 바뀌면 새 관리자 판단이 필요하다.

## 7. 예비조사자 ↔ 측정자(공시료) 서류 정합성

예비조사의 핵심 서류 정합성은 **예비조사자와 측정자(공시료)의 관계**로 평가한다.

- 단일일 측정은 예비조사자 중 **한 명이라도** 측정자(공시료)와 일치하면 match다.
- 다일 측정은 전체 측정기간 중 **최소 하루라도** 예비조사자 중 한 명과 해당 날짜의 측정자(공시료)가 일치하면 정상 match로 인정한다.
- 불일치는 실무상 가능하므로 hard fail하지 않는다.
- 같은 hard constraint와 균등 조건이면 match안을 더 높은 점수로 추천한다.
- 측정 참여자와 보고서 담당자는 이 match 점수에 사용하지 않는다.

측정자(공시료) 배정 우선순위는 다음과 같다.

1. 현재 배정수 균형
2. 예비조사자↔측정자(공시료) 일치
3. 동일주소
4. 실제 차량 동선
5. 안정적인 ID

한 사람이 두 번째 업체를 받기 전에 아직 0건인 배정 가능자를 우선한다. 6명에게 6개 업체를 배정할 수 있으면 기본 목표는 `1/1/1/1/1/1`이다.

## 8. 다일 측정

- `daily_staff`에 명시된 모든 실제 측정일을 사용한다. 시작일~종료일 사이 날짜를 임의 생성하지 않는다.
- 예비조사 plan은 사업장당 하나만 유지한다.
- 같은 사업장의 모든 실제 측정일은 동일한 예비조사일·방식·예비조사자·상태·확정정보를 공유한다.
- 날짜별 새 예비조사 plan을 중복 생성하지 않는다.
- 측정자(공시료) assignment는 실제 측정일별로 관리한다.
- 예: 한 사업장이 8/03과 8/25에 측정하면 두 날짜 검색에서 모두 노출되지만 예비조사 plan은 하나다. 8/03 기준으로 이미 유효한 예비조사가 있으면 8/25 때문에 새 plan을 만들지 않는다.

## 9. 기준 데이터 흐름과 표시

기준 흐름은 다음과 같다.

`measurement_target_business → 예비조사 plan/assignment → measurement_journal`

- 현재 target이 존재하면 측정일지 검색도 target의 유효 측정일과 lifecycle(`실시`)을 따른다.
- `미실시`·`거래종료` target에 연결된 과거 journal row는 삭제하지 않지만 현재 검색·표시에서는 제외한다.
- target 자체가 없는 순수 과거 이력은 이 기준으로 삭제하거나 수정하지 않는다.
- 측정 참여자와 보고서 담당자의 불일치는 별도 경고 대상이 될 수 있으나 예비조사자↔공시료 정합성 hard validation이 아니다.
- 예비조사 계획과 목록의 기본 표시 순서는 측정대상 사업장 관리의 canonical 기본 조회순서(상태 → 예정월 → 코드)를 공유한다.

## 10. 찐확정과 repair

- `measurement_journal` row가 존재하면 찐확정이다.
- `sequence_number`는 찐확정 판정 기준으로 사용하지 않는다.
- 찐확정은 일반 추천·재추천·수정·삭제를 차단한다.
- 찐확정도 현행 날짜 정책과 비교하여 정책 불일치 또는 mapping 오류를 검출한다.
- 관리자 또는 예비조사 담당자의 명시적 repair 경로에서 잘못된 필드만 최소 보정한다.
- repair 시 `measurement_journal`을 삭제·재생성하지 않는다.
- 측정예정일, 정상 예비조사자, 정상 공시료 assignment, 보고서 담당자, 측정 참여자 등 관련 없는 필드를 연쇄 변경하지 않는다.
- repair 전후 값, 사유, 수정자, provenance를 audit에 남긴다.
- 과거 당시의 불가 일정·용량을 재현할 수 없는 fallback 날짜는 자동 위반으로 단정하지 않고 수동 검토 대상으로 처리한다.

### 측정 참여자·보고서 담당자 source repair

- 측정 참여자와 보고서 담당자는 서로 독립적으로 보정한다.
- 선택하지 않은 역할, 예비조사자, 측정자(공시료), 측정일지와 과거 row를 자동 변경하지 않는다.
- before/after·사유·수정자를 audit에 남긴다.

## 11. 수동 수정·재추천·삭제

- 관리자 또는 `users.is_preliminary_survey_manager = true`가 추천·재추천·적용·일반 repair를 수행한다.
- 1인 3건 공시료 예외는 관리자만 수행한다.
- 일반 사용자는 조회 중심이다.
- 기존 V2 자동추천은 OFF 상태를 유지한다. 사업장 상세 저장만으로 V2 plan을 자동 생성·확정하지 않는다.
- 기존 manual plan도 현행 hard constraint를 다시 통과한 경우에만 minimum-change 대상으로 보존한다.
- 업체별 재추천은 같은 예비조사일의 조사자/조합, 방문·유선 용량, 동일주소·방문 묶음, 다일을 포함한 같은 실제 측정일의 공시료 균형 관계를 dependency closure로 확장한다.
- 찐확정은 dependency 계산에는 포함하되 일반 변경 대상에서는 제외한다.

### V2 plan 안전 삭제

- 찐확정되지 않은 persisted V2 plan은 예비조사 담당자 또는 관리자가 삭제할 수 있다.
- 삭제 대상은 `preliminary_survey_v2_plans`와 해당 plan에 귀속된 `preliminary_survey_v2_measurement_assignments`다.
- `measurement_target_business`, 측정예정일, `measurement_journal`, legacy 원천은 삭제하지 않는다.
- true-confirmed plan과 legacy reconciliation 또는 historical recovery 추적에 사용된 plan은 일반 삭제할 수 없다.
- 삭제 후 영향을 받는 공시료 assignment 그룹은 자동 2건 한도, 관리자 3건 예외, 4건 hard max에 맞게 같은 transaction에서 재정규화한다.

## 12. 저장·동시성·보안 불변식

- 측정자(공시료)의 authoritative source는 `preliminary_survey_v2_measurement_assignments`다.
- 과거 `recommendation_reason.measurementAssignee`는 read-only 표시 fallback일 뿐 새 write나 자동 backfill 근거로 사용하지 않는다.
- plan과 날짜별 assignment는 최종 wrapper RPC 한 transaction에서 저장한다.
- apply 서버는 현재 원천으로 예비조사와 공시료를 다시 계산하고 canonical draft, source fingerprint, 기존 assignment baseline을 비교한다.
- 클라이언트가 보낸 사용자 ID·이름·공시료 코드·승인 필요 boolean을 authoritative 판단 근거로 신뢰하지 않는다.
- 같은 측정일의 영향 assignment 그룹은 transaction advisory lock 등으로 직렬화한다.
- source/baseline이 달라지면 stale로 판단하고 0건 저장 후 재검토를 요구한다.
- 찐확정 guard는 plan/assignment의 INSERT·UPDATE·DELETE에서 OLD와 NEW target을 모두 검사한다.
- 관리자 repair 외 일반 경로에서 guard를 우회하지 않는다.
- 이미 적용된 migration을 고쳐 쓰지 않고 forward-only migration으로 수정한다.
- 운영 적용 전 비운영 DB에서 migration/RPC, rollback, 권한, 동시성, hard max를 검증한다.

## 14. 회귀 검증 사례

아래 사례는 정책을 구현·검증할 때 사용하는 **회귀 fixture**다. 실제 운영일정이 변하면 날짜는 다시 계산할 수 있으나, 이 사례가 검증하려는 역할 규칙을 임의로 바꾸지 않는다.

## 15. 운영지침 변경 절차

업무 규칙 변경 시 다음 순서를 지킨다.

1. 사용자가 최종 결정한 내용을 이 문서에 먼저 반영한다.
2. 문서 전체에서 새 결정과 충돌하는 과거 문구를 전수 검색해 **삭제한다.** 과거 규칙의 이력은 Git 커밋으로 추적한다.
3. 실제 사용자 예시가 있다면 회귀 fixture로 고정할지 검토한다.
4. 그 다음 코드·DB·테스트를 이 문서에 맞춘다.
5. Fresh verifier는 코드가 현재 문서를 구현했는지 독립 검증한다.

문서와 코드가 충돌하면 구현을 임의로 정답으로 간주하지 않는다.
